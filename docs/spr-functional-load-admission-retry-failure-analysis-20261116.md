# load admission/retry 首轮失败分析与低成本近似方向

**后续回退：** 用户已要求撤回失败实现；P0/P1/P2 的工作代码、专属配置和测试已移除并按冻结身份归档。新的默认关闭候选及验证见 [稀疏 load 批次下界](spr-sparse-load-pressure-validation-20261116.md)。下文保留原方案/实验历史，不能据此认为旧候选仍在当前代码中。


日期：2026-11-16。状态：**失败复盘和替代方案，未实施新模型。** SPR-M4 和安装 ELF 保持不变，P1/P2 继续关闭。本文补充 [首轮验证](spr-functional-load-admission-retry-graph500-validation-20261116.md)，不覆盖原始负面结果。

## 1. 判断

这次失败包含两个不同问题：

1. **模型收益假设没有成立。** 原生 MemRead 额外发射和响应侧预约冲突，不等价于遗漏了相同数量的关键路径周期。Graph500 P1 的 CPI 误差恶化，P2 增加的失败预约没有增加最终时序效果。
2. **成本粒度偏细。** 为修复 load 接收问题，在第二阶段重新给几乎全部 UOP 维护共享执行资源日历。按事件跳转消除了逐空闲周期扫描，但没有消除每 UOP 搜索、登记、清理和复制的成本。

因此不建议继续把全量 FU 日历作为默认方向工程化。它可以保留为显式诊断对照。下一步应先证明某种资源限制确实在 CPI 关键路径上缺失，再用资源组/阻塞区间的解析下界和少量局部反馈近似。

此前方案对“修复预约一致性→获得 CPI 收益”的预期过高，应当修正。预约守恒仍是有价值的机制检查，但不能代替准确率和吞吐验收。

## 2. 已核对的结果

数据来自保存的 quick 评分和同一计时 ELF 的六个 OFF/P1/P2 收据，没有新增其他负载回放。

| 案例 | gem5 CPI | M4 CPI / AE / RE | P1=P2 CPI / AE / RE | P2 E2E 速率变化 | P2 纯模拟速率变化 |
|---|---:|---|---|---:|---:|
| C4 Graph500 | 0.966422 | 0.839507 / 0.126915 / −13.132% | 0.837612 / 0.128810 / −13.329% | −19.149% | −27.376% |
| C8 Graph500 | 0.969791 | 0.851812 / 0.117979 / −12.165% | 0.844982 / 0.124809 / −12.870% | −15.609% | −22.953% |

AE=`abs(FastSim CPI−gem5 CPI)`，单位 cycles/macro；RE=`(FastSim−gem5)/gem5`。两例等权 MAE **0.122447→0.126810**，MAPE **12.649%→13.099%**。不是略有精度收益，而是整体恶化。

E2E 使用本次 [计时合同](trace-comparison-throughput-contract-20261116.md)：输入准备和 warmup 计入，额外可靠性审计独立计时。两例总 user UOP/总 E2E 秒的汇总速率变化为 **−16.871%**。纯模拟是辅助速率，不能将“模拟耗时增加 37.696%/29.791%”误写为吞吐下降同样的百分比。原吞吐只有每例一组，不能估计重复波动或充当正式吞吐验收。

P1 已承担 P2 相对 OFF 新增纯模拟墙钟的约 **90.26%（C4）/89.22%（C8）**。这只是阶段墙钟差值的分解，不是 CPU 采样因果归因。

## 3. 为什么吞吐下降

### 3.1 全量预约造成工作量放大

源码 [第二阶段非内存预约](../src/simulator.cpp#L16249-L16261) 对每个处理的 UOP 推进日历水位，并为未被 rename 消除的非内存 UOP 预约资源。普通 load 也进入新日历，特殊成员保留观察路径。

| 测量段预约 | C4 | C8 |
|---|---:|---:|
| P1 reservations | 40,001,651 | 79,972,435 |
| P2 额外失败 reservations | 4,889,244 | 9,397,178 |
| P2 reservations 总量 | 44,890,895 | 89,369,613 |

这不是仅在少数 load 受阻时处理一个事件，而是近乎全部 UOP 都多走一遍资源安排。第一阶段已有的 FU/依赖安排和第二阶段新日历分属不同时间基准；新增约束虽有一致性目的，计算工作却真实重复。

### 3.2 数据结构和查询常数也偏大

[FunctionalIssueCalendar](../tmp/sparse-load-pressure-20261116/before/include/fastsim/functional_issue_calendar.hpp) 中：

- `reserve()` 先调用 `first_available()`，随后 `observe()` 内再调用同一查询，并另行查找可用候选端口。
- 每 UOP 的 `prune()` 处理三个 `std::map`、12 个端口区间 vector，以及同类 interval 结构。
- 每次登记涉及树查找/节点维护、区间合并、vector 插入删除；窗口进入和提交还复制 live 日历。
- 65,536 live 上限限制的是状态规模，不是每条功能事件的宿主执行成本。

优化容器或消除重复查询能降低其中一部分开销，但不会自动产生缺失的 CPI 收益。首先应降低需要处理的事件数量和模型粒度。

### 3.3 本次新增热点采样

使用冻结计时 ELF `dd7815cac8513c58ed76dbbd6de533d758110085abe1d85cfcb4bf13a40c948c`，只对 C4 做 OFF/P1/P2 三次串行采样：`perf record -e cpu-clock:u -F 99 --call-graph dwarf,4096`。仍通过现有输入收据校验和 `run_high_frequency.py` 使用 CPU 52–63。三个模式的完整 `time_accounting` 和 `cores` 均与其原收据相同。

| 用户态 CPU self 样本 | OFF | P1 | P2 |
|---|---:|---:|---:|
| calendar first_available | 0 | 6.63% | 7.40% |
| calendar observe | 0 | 3.84% | 4.55% |
| calendar prune | 0 | 3.06% | 3.44% |
| 三者合计 | 0 | **13.53%** | **15.39%** |

这些是整进程用户态 CPU 样本的互斥 self 占比，不是并行墙钟比例，也不包含所有调用者、内联代码、分配和复制中的关联成本。不能从 E2E wall 直接减掉 15.39%，或把本次带 profiler 的时间当作新吞吐结果。它们确认了日历是实际宿主热点。

### 3.4 已排除的过度解释

- 输入准备基本未增加，主要新增阶段成本在模拟和 warmup。
- C4/C8 的峰值 RSS 没有与耗时相当的大幅增长；不能把这次下降主要归因于新增几十 GiB 内存或输入换源。
- 代码会因 admission 禁用 inactive-segment/causal-block shortcut，但本批 OFF 已启用分区 IQ，且 v2-wait 在用，相关 shortcut 原本就被前置条件拒绝。**不能将“关掉已有快速路径”列为本批已证实主因。** materialized fast kernel 的配置在 OFF/P1/P2 中均为 true。

## 4. 为什么 CPI 没有改善

### 4.1 失败尝试被已有接收等待吸收

P1 直接等已有 Sequencer callback，再预约成功发射。P2 增加一次提前失败预约，然后仍跳到该 callback 附近预约成功发射。

以只有一条 load 的简化情况说明：假设接收槽在周期 100 才可用，P1 的成功尝试为 100；P2 在 20 失败、100 成功。如果这次失败既没有推迟其他关键指令，也没有改变接收/返回边界，退休时刻自然相同。做了更多宿主计算，不意味着目标程序一定多花周期。

本批计数符合这一模式：

| 案例 | P2 相对 P1 的 FU 累计等待变化 | 接收累计等待变化 | 最终 time_accounting |
|---|---:|---:|---|
| C4 Graph500 | +19,180,492 | −19,180,492 | 完全相同 |
| C8 Graph500 | +37,661,602 | −37,661,602 | 完全相同 |

重新核对归档十例，**十例 P1/P2 的完整 time_accounting 全部相同**。本次没有重跑这些其他负载。不能从最终核算相同推导每条 load 的接收时间也相同；累计等待和也不是 CPI，但结合源码足以说明现有 P2 在测试范围内没有产生独立的最终收益。

### 4.2 预约冲突数不是缺失关键路径时间

P0 的 C4/C8 冲突分别约 637 万/1211 万，P1 降到 60/100，却没有改善 CPI。这里观察的是模型响应时刻投影到自建日历后的容量冲突，不是原生 FU grant 与硬件 stall 的逐条守恒比较。

同一等待链可以在很多 UOP 上重复表现为冲突；对后续指令重新安排，也可能只是把已有接收等待转移到其他环节。冲突修正成功不能证明原误差来自这些冲突。

原生 MemRead 发射/退休 load 约三倍仍然是待解释的诊断现象，不能按这个倍率制造重试或罚时。当前 P2 只允许每 load 一次失败尝试，也没有复现原生全部重发原因；本结果否定的是“这个已实现近似具有实际收益”，没有证明所有可能的重试机制都无影响。

### 4.3 局部精细安排没有解决共享服务近似

P1/P2 改变本地尝试与接收时刻，共享 cache/DRAM 仍按既有一次提交顺序处理。代码 [共享迟到检查](../src/simulator.cpp#L16830-L16845) 只记录相对已提交共享起点的偏移，不重新求解共享排队。

两例 P1/P2 的共享迟到事件分别为 190,747/388,548，最大约 3,021/3,031 周期。累计量 31,930,975/65,006,492 有重叠，不能加成 CPI。它们说明局部详细化没有关闭原有共享到达近似，不能据此认定共享迟到已解释全部残差。

P1 相对 M4 的 active cycles 总和减少 C4 **58,942**、C8 **424,840**。新增约束在既有近似、时刻位移和重叠关系下不保证最终 CPI 单调增加。准确率恶化是直接可观察的结果；其逐 load 的因果分解尚未完成。

## 5. 设计应如何收缩

### 5.1 保留的部分

- 已有 Sequencer 成员额度、返回事件、依赖和队列反馈。
- 功能人口、服务身份和事件生命周期的守恒检查。
- 全量日历作为显式诊断工具，用于小规模采样，不放入默认热路径。

### 5.2 不再作为主线的部分

- 所有 ALU、branch、load 的第二遍精细预约。
- 每条受阻 load 都登记一次不会产生额外关键路径效果的失败尝试。
- 为降低内部冲突计数而继续增加执行细节，或通过经验 replay 倍数/固定延迟弥补 CPI。

这不是撤销现有 TLB 或设备机制。两者的来源和验证与本候选分开，当前 M4 保持。

### 5.3 推荐近似：只计算尚未覆盖的资源瓶颈下界

保留现有两阶段和响应路径。在已有 chunk/阻塞区间内汇总少量资源需求，不再为每个 UOP 维护时间树：

1. **先做廉价筛选。** 复用已有接收槽等待、返回、队列峰值及依赖链信息。无接收受阻、无新增带宽下界、无关键依赖暴露的区间沿用旧结果。
2. **按已知资源组计数。** 普通 load 的成功接收需求、发射宽度需求、就绪批次大小按功能身份汇总；第一阶段已有非内存执行需求直接复用，第二阶段不重新逐条安排它们。
3. **只合并下界。** 示意为 `T_new = max(T_existing, T_load_service_bound, T_issue_bound, T_dependency_bound)`。它不是完整 CPI 公式，但明确禁止把彼此重叠的等待再线性相加。容量和 issue interval 来自目标配置，不为 Graph500 调参。
4. **仅在短期突发可能受限时细化。** 使用请求释放批次和目标队列容量切分局部区间，避免全窗口平均掩盖突发；状态为固定小数组/队列摘要，无全 UOP map。端口能力交叠按已验证组处理，不把所有 FU 容量简单相加。
5. **对实际暴露的界反馈。** 新下界若已被现有接收/依赖等待覆盖，则不改变 CPI，也不追加 retry 罚时；只有多出的暴露部分沿现有依赖和完成反馈前推。

第一版不使用原生三倍发射量，不新增经验重试需求。只有后续证明某类拒绝后的执行资源占用会推迟关键就绪批次，才根据模型自身的阻塞/释放事件估计附加需求。此方向允许得出“retry 无需额外时序模块”的结论。

这种抬高抽象、以 miss/阻塞区间和解析瓶颈替代细粒度执行细节的取舍，与 [interval simulation 的方法](https://biblio.ugent.be/publication/845663) 一致。该论文不证明本项目新方案的精度或吞吐。共享到达顺序的近似仍需单独量化，不能为消除它恢复整窗口收敛；[Sniper 的因果近似说明](https://snipersim.org/w/Causality) 也把并行效率和共享时序误差作为显式取舍。

## 6. 下一轮的停止条件和工作顺序

1. **先诊断关键路径，不先写替代大模块。** 区分首次尝试、实际接受、返回就绪与退休，比较同起点的模型/gem5 诊断；原生时刻只用于离线定位，不输入模型。优先判断服务时刻、在途持有与队列暴露哪一项真正缺失。
2. **只做 Graph500 C4/C8 的最小对照。** 对一个假设改变一个机制，先检查它是否改变未覆盖的完成/退休下界。原生 PMU/硬件证据不足仍为 unavailable。未授权扩展的吞吐矩阵不恢复。
3. **先过成本门槛再扩展。** 建议下一版开发目标为 E2E 吞吐下降不超过 3%、纯模拟下降不超过 5%；这是建议门槛，尚非用户确认或已经通过的验收标准。候选若精度没有稳定改善，收益门槛为零容忍：不接受仅为内部指标好看付出额外成本。
4. **分清验证层次。** 先小规模配对估计成本和噪声，值得继续才做约定的正式吞吐验收。报告必须同时包括 CPI AE、MAE、相对误差，不能拿冲突减少或计数守恒代替精度。
5. **保留负面结果。** 当前 P1/P2 不默认开启，不删除原实现/冻结证据，也不把容器优化后的版本直接称为精度修复。
