# TSim v26.1 训练集构造方案

状态：设计与代码实现同步。本文档记录不重跑 gem5、复用现有 raw trace pool
（含新加入的 c32_seedA）的前提下，v26 训练集重构的完整方案：负载集组织、
切窗策略调整、抽样与去重规则、代码改动清单、落地步骤。

## 1. 目标与范围

**目标**：在现有 16 workload × 5 core count (c01/c04/c08/c16/**c32**) × cfg=A0
的 raw trace pool 上，构造一份**每 slice 内部同构、关键窗口有下限保证**的
训练集，替代 `data/windows_v26_clean14_tail_local_all`。

**不做**：不重跑 gem5、不新增 workload、不新增 uarch。这些留给 v27
（见 `docs/v27_workload_set_design.md`）。

## 2. v26 现状问题（已在数据上量化）

| 问题 | 证据 |
|---|---|
| workload 内部不同构 | `W_chase_dram @ c16` CPI 分布 min=0.35 / p50=2.36 / max=22.7 |
| 关键窗口漏抽 | `W_chase_dram @ c16` CPI∈[3,10] 相变段仅 59 行 (2.7%) |
| 极端 CPI 塌到一个 workload | CPI≥40 的 744 行 100% 来自 `W_false_sharing @ c16` |
| c01 基线严重欠采样 | `W_compute_int @ c01` 只有 584 行；`W_false_sharing @ c01` 只有 760 行 |
| c32 缺失 | v26 训练集没有 c32 slice（用户已重新采集 raw trace） |
| 长 macro 触发跨核 skew | quota 路径 `_prev_macro_end` 对 REP-prefix / gather 展开的几千条 µop macro 会无限回退 |

## 3. 设计决策

### 3.1 每 workload 内部同构

**做法**：按 label 空间对 6 个高变异 workload 做**后处理拆分**，把内部不同
物理机制的窗口打成不同的逻辑 workload。原 `workload` 字段保留作业务标签，
新增 `workload_variant` 字段承载拆分标签，训练时用 variant 做 slice cap
和 embedding。

**拆分表（c32 感知）**：

| 原 workload | 拆成 | 数 |
|---|---|--:|
| W_chase_dram | W_chase_low(<3), W_chase_mid(3-10), W_chase_high(10-25), W_chase_extreme(≥25) | 4 |
| W_false_sharing | W_fs_low(<10), W_fs_mid(10-25), W_fs_high(25-45), W_fs_extreme(≥45) | 4 |
| W_stream | W_stream_low(<8), W_stream_high(8-20), W_stream_extreme(≥20) | 3 |
| W_feed_ranking | W_feed_low(<8), W_feed_high(≥8) | 2 |
| W_fp_compute_dense | W_fpcd_low(<5), W_fpcd_high(≥5) | 2 |
| W_ads_ctr | W_adsctr_low(<3), W_adsctr_high(≥3) | 2 |
| 其它 10 个 | 保持原样 | 10 |

**16 原 workload → 27 逻辑 workload**。新增的 `_extreme` 档专门覆盖 c32 上
拉高的 CPI 分布（例如 `W_fs_extreme @ c32` CPI 60+）。

**为什么拆分**：不是为了 dedup，主要是让 `per-workload-cap` 能对稀有物理
机制单独设配额、让每 slice 内部签名同构，让抽样机制"每 (wl, nc) 生成 5000
raw window" 的模型正确匹配到"每种机制都有单独 5000 采样"。

### 3.2 切窗允许在 µop 边界（跨 macro）

**问题**：原 `_prev_macro_end` 从 T_end 无限回退到上一 macro 边界；碰到
REP-prefix (`REP MOVSB`)、gather (`VPGATHERDD`)、microcode fallback (int-div
展开) 等**几千条 µop 的长 macro**时，某核回退量对应几万 cycle，跨核 T_end
skew 被系统性放大。

**关键观察**：主 label `cpi_uop = (max_commit_tick - min_commit_tick) / uops`
只依赖 µop commit_tick 与 µop 计数，**天然允许在任意 µop 边界切**；PMU
counter (branch_miss/l1d_miss/…) 是每条 µop 独立累加，同样与 macro 边界
无关。macro-snap 只影响诊断字段 `cpi_macro / mpki_br / mr_l1i`（这些字段
不在 `PMU_KEYS`，不进训练 loss）。

**改动**：`_prev_macro_end` 增加 `macro_snap_max_retreat` 参数（默认 32
µop）：
- 短 macro（<32 µop）依然 snap 到 macro 边界（保 `cpi_macro` 精度）
- 长 macro 触发 max-retreat 保护，直接在 µop 边界收口
- 跨核 T_end skew 上界从"数万 cycle"降到"O(几百 cycle)"

`take_macro_window_by_budget`（quota 路径的向前装窗）同步加同一个开关。

`build_samples_tq`（TQ 主路径）**本来就在 µop 边界切**——它用
`bisect.bisect_right(ticks[c], T_end)` 找 end，从来没有 macro-snap。原
docstring "commit_tick <= T_end 的最后完整 macro" 是过时描述，本轮修正。

### 3.3 Dedup 加 CPI 硬保留规则

**问题**：z-score L2 阈值 0.05 只看 core_summary / opclass 特征，对
"输入相似但 label 差异大"的窗口会误删。相变段窗口特别容易被认为是
"稳态窗口之间的过渡"而丢掉。

**改动**：`_dedup_shard` 在 z-score dedup 前加两条硬保留规则：
- `mean_cpi >= 30 or mean_cpi <= 0.35` → 无条件保留（覆盖尾部两端）
- `3 <= mean_cpi <= 10` → 无条件保留（覆盖当前稀疏的中段）

预期：CPI≥40 从 744 行 → 保留 raw 中所有 ~3000 行；CPI 中段从 59 行 →
数千行。

### 3.4 分级 `--per-workload-cap`

按 27 个逻辑 workload 分档：

| slice 类型 | cap（c04/c08/c16/c32） | c01 加权（×1.2） |
|---|--:|--:|
| 相变段（W_chase_mid, W_fs_mid） | 2500 | 3000 |
| Extreme 段（W_fs_extreme, W_chase_extreme, W_stream_extreme） | 2500 | 3000 |
| 稳态拆分段（chase_low/high, fs_low/high, stream_low/high, feed_*, fpcd_*, adsctr_*） | 2000 | 2400 |
| 未拆的 10 个低变异 workload | 1500 | 1800 |

**c01 加权 1.2×** 的理由：单核基线是"无多核干扰时的 workload intrinsic
CPI"，多采一点能给模型学到 core→CPI 曲线的起点锚。

### 3.5 Raw window 上限提到 10000

- 现在 `--tq-target-windows=1200` 实际每个 (wl, nc) 生成 ~5000 raw window
- 提到 **10000** 让稀有 slice 在 dedup + cap 之后仍有充足样本
- 存储成本：`windows.jsonl` 从 ~38 GB → ~60 GB，可接受

### 3.6 MAX_LEN 与 max-uops-per-core

- **MAX_UOPS_PER_CORE=32768**：保持（记忆里已记录 v26 时代 c16 有 L=19066
  的窗口，c32 需要同样保护）
- **MAX_LEN=32768**：保持当前 v26/v26.1 训练和推理路径一致，不额外引入
  65536 cache/model 配置。c32 上超过 32k 的窗口在 build 阶段丢弃。
- **原因**：本轮目标是验证 workload_variant + cap/dedup 的数据分布修正，
  不同时改变上下文长度带来的显存/吞吐和训练配置变量。

## 4. 代码改动清单

改动文件：`data/build_windows.py`（本次已实施）。

### 4.1 `_prev_macro_end`（L1395-1420）

- 新增参数 `macro_snap_max_retreat: int = 32`
- 语义：
  - `>0` 且当前位置到上一 macro 边界的回退 ≥ max_retreat → 不回退，返回
    orig_end（µop 边界）
  - `=0` → 完全禁用 macro-snap，直接返回 end
  - `<0` → 保持旧行为，无上限回退

### 4.2 `take_macro_window_by_budget`（L1328-1392）

- 新增参数 `macro_snap_max_retreat: int = 32`
- token budget 满时的 fallback：
  - 已见完整 macro 且回退 ≤ max_retreat → snap 到 last_safe_end（旧行为）
  - 已见完整 macro 但回退 > max_retreat → 在当前 µop 边界收口
  - 从未见完整 macro（当前位置深陷长 macro）且已过 max_retreat →
    在 µop 边界收口，避免丢窗口

### 4.3 `take_macro_window_back_by_budget`（L1430-1461）

- 新增参数 `macro_snap_max_retreat: int = 32`
- 传递给 `_prev_macro_end`

### 4.4 `build_samples_quota` + `process_workload`

- 新增参数 `macro_snap_max_retreat: int = 32`，向下透传到
  `take_macro_window_by_budget`

### 4.5 `build_samples_tq` docstring 修正

- 老 docstring 说"最后完整 macro"，实际实现是 `bisect_right`（µop 边界）
- 已改为清晰说明"µop 边界，不 macro-snap；诊断字段 cpi_macro 有 <1% 系统误差"

### 4.6 新增 CLI flag `--macro-snap-max-retreat`

- 默认 32
- 通过 `main()` argparse 定义并透传到 `process_workload`

### 4.7 待做（下一次落地）

以下变更在本设计文档已明确，但**代码尚未实施**，需要在跑 v26.1 build 之前
补上：

- **`_relabel_by_cpi`（新函数）**：在 `encode_multicore_sample` 生成 sample
  之后写入 `workload_variant` 字段，用 mean CPI 做拆分
- **`_dedup_shard` 加 CPI 硬保留规则**：CPI 极端 + 中段无条件保留
- **`_parse_per_workload_cap`**：改用 `workload_variant` 做 key（保持向后
  兼容原 `workload` 名字）
- **`_extract_feature_vec` 保持不变**：dedup 特征依然用原 workload 内的
  z-score，避免逻辑 workload 拆分后特征基线错位

## 6. 预期效果

### 6.1 关键窗口覆盖对比

| 关键窗口 | v26 现状 | v26.1 预期 |
|---|--:|--:|
| c01 W_compute_int（基线） | 584 | 1800 |
| c01 W_false_sharing baseline (W_fs_low) | 760 | 2400 |
| CPI 3-10 中段（W_chase_mid c16） | 59 | ~2500 |
| CPI≥40 极端（W_fs_extreme c16） | 744 | ~2500 |
| c32 训练样本 | 0 | 27 × 2000 avg ≈ 54k |
| 每 slice 最少样本 | 584 | ≥1500 |
| 总窗口数 | 220k | ~250k |
| 长 macro 引发的跨核 skew | O(数万 cycle) | O(几百 cycle) |

### 6.2 标签精度影响

- `cpi_uop`（主 label）：**无变化**——本来就是 µop-level
- PMU counts（次 label）：**无变化**——本来就是 µop-level 累加
- `cpi_macro`（诊断字段）：**< 1% 系统误差**——首尾 macro 中间切时
  instr_retired 少 1
- `mpki_br / mr_l1i`（诊断字段）：**< 1% 系统误差**——分母同 cpi_macro

## 9. 与 v27 完整方案的关系

| 方案 | 时长 | 覆盖 |
|---|---|---|
| **v26.1（本文档）** | 1-2 天 | 复用现有 raw；修复关键窗口漏抽 + slice 均衡 + µop 边界切 + c32 |
| **v27 完整重构** | 4-5 周 | 上述 + 20 个内部同构 workload + 5 uarch + 显式相变 workload + cross-core 不均匀 |

**建议路径**：先做 v26.1 拿到快速验证信号（尤其是"内部同构逻辑
workload + 分级 cap"是否能显著改善 CPI 中段和极端段预测）；如果验证有效，
再投入 gem5 重跑做 v27。

## 10. v26.1 无法解决的问题

以下依赖重跑 gem5，本方案不覆盖：

- cross-core 不均匀（skew）workload
- 冷启动 / mixed workload
- 多 uarch (A1-A4) 训练
- 显式相变 workload（虽然逻辑拆分能让"CPI 中段"进独立 slice，但相变过程本身
  依然是从 raw trace 里挑出的、稀疏的、不受控的样本；v27 用受控 gem5 workload
  可以精确控制相变时长和幅度）
