# Zstd CPI 大误差：排查过程与通俗解释

日期：2026-10-20。本文整理已有采集、诊断及修复证据，不代表重新运行实验。范围是标准 SPEC `777.zstd_r`、4 个单线程 rate 副本、4 核、8 内存通道、buffer TSO 114。不能将结论直接推广到 SQLite、LBM 或所有负载。

本次发现了两个相连的问题：**trace 没有说明某类微操作只检查地址、不写数据；FastSim 因而也没有保留这类操作对后续 store 提前准备的限制。** 修复功能语义并加入响应侧约束估计后，同一份新 trace 的 CPI 误差从 -26.89% 缩小到 -8.82%。严格请求扫描和页表服务尚未补齐，因此这是阶段性修复。

## 1. 先解释：CPI 误差“崩了”是什么意思

CPI 可以理解成“平均完成一条程序指令，需要多少个 CPU 活跃周期”。这里一条指令指宏指令，即程序看到的指令，不是处理器内部拆开的微操作。

```text
Active CPI = 负载线程占用 CPU 期间的活跃周期总数 / 同期宏指令总数
相对误差 = (FastSim CPI - gem5 CPI) / gem5 CPI
绝对误差 = abs(FastSim CPI - gem5 CPI)，单位 cycles/宏指令
```

误差为负，表示 FastSim 预测得过快。假如两边执行同一批指令，gem5 平均需要约 1.47 个周期，FastSim 只算约 1.08 个周期，问题就是少算了执行过程中的等待，或者把本来不能重叠的工作过早重叠了。

Elapsed 是这段负载从开始到结束经过的目标系统时间，不是四核时间之和，也不是采集工具在宿主机上跑了多久。采集花几百秒，目标窗口只有几毫秒，两者并不矛盾。CPI 使用 active，报告另外列 elapsed。

以前某个 LBM C4 只有约 5% 的误差，不能保证 Zstd 也如此。不同负载会走不同的代码和微架构路径；在 LBM 上影响较小的缺口，可能被 Zstd 的批量复制代码反复触发。没有同配置、同输入的机制对照，也不能断言历史小误差一定来自误差抵消。

## 2. 为什么不能一开始就加延迟，把 CPI 调回去

这像两块表显示不同时间：先确认两块表测的是同一段过程，再检查哪里计时有误。直接把慢表拨快，数字会接近，但原因仍然存在。

本次先固定以下条件：四个标准 rate 副本、不额外启用 OpenMP；相同核数、八通道、cache/FU 参数和 buffer TSO；KVM → warmup → stat；合法共同终点；同一 workload-task 统计范围；宏指令与 UOP 数量分别守恒。

微架构参数取自实际采集配置，不为了缩小 CPI 误差增加常数。Cache 参考来自独立审计的 Ruby/SLICC native 摘要，不拿 trace 里的路径分类代理当真值。目标硬件身份检查与 native validator 分开执行；后者的 `passed` 不等于准确率达标。

修改 gem5 后，要重建绑定新二进制身份的 checkpoint 并重采。即使从相同起点运行，OS 和多核交错也可能使自然共同终点不同。因此，不同采集窗口只分别报告；**修复前后模型的效果，用同一份新 FST 做对照。**

## 3. 先处理了两项上游问题，才进入本轮排查

早期 Zstd 的 ROI 曾覆盖不合适的执行阶段，后来移到实际压缩计算区，并检查逐核分段的代码构成。修正 ROI 后，仍有明显低估，所以“标记位置正确”不等于模型正确。

随后发现 gem5 的 NT-store 实现中，一个本意是提示的 `warn_once` 会经 MicroDebug 进入 O3 trap 路径，引起排空、流水线清空和重新取指。通俗地说，本来只想打印一句提示，却让模拟 CPU 按异常流程停下来处理。

这项 producer 修复去掉了非架构调试 trap，保留数据、地址检查和真实坏地址 fault，并用新 checkpoint、新 trace 复验。此后仍有明显 CPI 低估，说明还有独立的模型问题。不能把历史窗口与本轮窗口当成同一份指令流上的单次改善。

LRU 驻留证书也做过受控检查。在去除调试 trap 后的同一历史源上：

| 历史源配置 | gem5 CPI | FastSim CPI | 相对误差 | CPI 绝对误差 / 单案 MAE |
|---|---:|---:|---:|---:|
| 默认 | 1.500908 | 1.083942 | -27.78% | 0.416967 |
| 仅开启 LRU 证书 | 1.500908 | 1.001608 | -33.27% | 0.499300 |

绝对误差与 MAE 单位为 cycles/宏指令。证书只能证明它所覆盖的驻留条件，不能替代地址翻译、store 队列和完成顺序，因此没有默认开启它。

历史阶段的具体来源与数值见[采集与早期修复记录](spec-rate-sqlite-zstd-collection-20261016.md)。下文重点是这之后仍然存在的低估。

## 4. 第一步：给整个窗口做一张“不重复算时间”的账

沿用[9 月排查方法](buffer-tso-cpi-diagnosis-next-steps-20260924.md#8-下一步工作与验收顺序)，先定位周期差在哪里，再判断原因。

在原始成功采集上还分别试过分支恢复和 store lifecycle：前者补回 862,999 active cycles，约为原周期缺口的 9.86%；后者补回 449,631，约为 5.14%。它们值得修正，但单独不足以解释大缺口。这是两个独立开关的净效果，不能相加当作互斥的原因贡献；具体 CPI 与绝对误差见下面链接的原始诊断报告。

处理器会同时执行很多条指令。如果三条指令同时等待 100 周期，实际可能只经过 100 周期，不能把等待相加成 300 周期。本次按相邻退休边界，把时间互斥分成：有指令退休、下一条尚未取指、已取指但尚未最终发射、load/store/其他指令已发射但尚未退休。

这里“退休”是处理器确认指令结果可以按程序顺序生效；store 退休后，数据写出和队列释放还可能继续等待。

对同次诊断窗口进行逐核指令配对后，主要差额如下。正数表示 gem5 用时更多；这些是时间落点，不是已证明的原因贡献。

| 互斥时间分区 | gem5 比 FastSim 多出的周期 |
|---|---:|
| 有退休的周期 | 1,708,259 |
| 下一退休指令尚未取指 | 39,856 |
| 已取指、尚未最终发射，含翻译与重试 | 4,675,435 |
| load 已发射、尚未退休 | 1,625,505 |
| store 已发射、尚未退休 | 391,924 |
| 其他已发射、尚未退休 | 186,158 |
| 未知阶段 | 33 |
| 已配对退休跨度差合计 | 8,627,170 |

再纳入窗口起止、共同终点和线程归属修正，才得到正式 active 周期差 8,485,487.879880。这避免了把物理核跨度与负载 active 周期混算。

这次阶段取证的外层协调器在正常 EOF 后误发 SIGTERM，原始退出收据保留失败状态。虽然独立检查确认窗口、记录和 native 响应闭合，它仍只用于诊断，不能升级成成功的正式采集。后续修复验证使用另一次正常退出的新采集。

完整分区与退出竞态说明见[退休周期诊断](zstd-cpi-retirement-diagnosis-20261019.md)。

## 5. 第二步：检查是不是指令太少、冷启动太严重

假设是“刚开始 cache/DTLB 都没热起来，FastSim 没有准确还原启动成本”，就应优先检查误差是否集中在窗口开头。

把每核测量记录按顺序等分为八段，四核对应段相加，得到：

| 顺序段 | gem5 − FastSim 退休跨度，cycles |
|---|---:|
| 1 | 452,691 |
| 2 | 1,004,937 |
| 3 | 590,977 |
| 4 | 2,732,712 |
| 5 | 654,655 |
| 6 | 1,341,901 |
| 7 | 1,684,524 |
| 8 | 164,773 |

首段只占总差额约 **5.25%**，最大差出现在第 4 段，第 6、7 段也明显。因此，当前证据不支持把主要误差归结为“窗口太短，只有开头冷启动没模拟好”。

这项检查没有证明所有工作集都已预热收敛；要判断那一点，仍需独立的 warmup 长度扫描。但它告诉我们：继续盲目延长 warmup，未必能修复中后段反复出现的问题。

## 6. 第三步：把大差额定位到 NT-copy 区段

完整诊断窗口中有 20 段以同一函数的 `SFENCE` 结束的 NT-copy 区段。这些互不重叠的区段，退休跨度差合计约 **513.62 万周期**，规模相当于 active 周期缺口的 **60.53%**。

这说明批量复制是优先排查位置，但不证明“60.53% 全是某一种 store 错误”。区段中仍有少量内核活动，翻译、队列、数据服务也会互相影响。gem5 此处仍把 NT-store 当 cacheable fallback，没有完整模拟真机 write-combining，结论首先针对 gem5 与 FastSim 的对齐。

随后纠正了一个容易误读的日志字段：`O3PipeView.issueTick` 记录的是**最后一次发射**，重试会覆盖之前的时间。看起来“很晚才发射”的指令，可能早就发射过，只是一直在等待翻译完成后重试。

短段日志中的同一条 CDA，第一次已经 ready 并发射，无预测内存依赖；约 **505 周期**后再次发射，才进入后续写路径。源码对应 translation-delayed → deferred → translationCompleted → ready。它证明至少存在真实的翻译等待与重试，不能把这段间隙统统解释为 IQ 没准备好，也不能把 505 周期再加进已经守恒的退休账。

## 7. 第四步：发现 CDA 的“身份”在 trace 中丢了

在本次 gem5 的微操作展开中，一条 `MOVNTDQ_M` 包含 CDA 地址检查和后续实际数据 store。CDA 可理解为“先检查目的地址是否允许访问”。它有地址、有大小，在一些分类中也带 store 属性，但有一个决定性的标记：`Request::NO_ACCESS`。

这个标记的意思是：**该请求本身不执行普通的数据 cache 访问。** 地址翻译仍可能访问页表，所以“不写数据”不代表它没有译址成本，更不代表可以从 CPU 指令流中删除。

旧 FST 记录了 store、地址和大小，没有记录这个区别。FastSim 因而会按普通数据 store 处理 CDA，产生不该有的 cache 流量，也缺少本地请求对后续提前准备的约束。

| CDA 的责任 | 应保留吗 |
|---|---|
| CPU 执行、寄存器依赖、宏/UOP 身份 | 保留 |
| 地址检查、DTLB/翻译路径 | 保留 |
| store queue（SQ）结构占用与顺序 | 保留 |
| 普通数据 cache 写请求、dirty 更新、虚构的转发数据 | 不产生 |

不能简单删掉 CDA；那样既会少算 CPU/队列工作，也可能改变指令数量，把错误藏进 CPI 分母。

## 8. 为什么“多算了 cache 写”，CPI 反而会偏低

用排队办理业务来理解：CDA 像队列里的验票步骤，后面的 store 才是真正办理业务。验票本身不用去数据仓库，但仍占队列位置。gem5 的可选 prepare 扫描遇到本地请求时，会停在这里，不能越过去替更年轻的 store 提前准备。

`prepare` 类似提前取得某条 cache line 的写权限，可以与其他工作重叠；它不等于已经把 store 数据写出去。`canWB` 可以理解成“满足执行和顺序条件后，允许进入写出处理的时点”。

旧模型没有表达 CDA 的本地身份和扫描限制，可能让后续写入过早准备。即使它额外生成了一些虚假 cache 请求，过度提前和重叠的效果仍可能更大，最终预测过快。**请求更多，不保证总时间更长；完成顺序和重叠程度同样决定 CPI。**

本次修复分两部分：一是把“只验票、不写数据”的身份传给 FastSim；二是在响应侧估计中，让年轻请求的准备时间受自己的 canWB 和前面本地操作完成时间约束。前面的限制已经过去后，不继续强加等待。

```text
准备准入时间估计 >= max(自己的 canWB 时点，前面本地操作完成时点)
准备完成时间估计 >= 准入时间估计 + 原有服务时间估计
```

这不是直接给每条 CDA 加一个拟合出来的罚时，而是恢复它与后续操作之间缺失的先后约束。但当前仍是**响应侧估计**：cache 请求真正进入层次的时刻、命中路径和资源竞争尚未完整随之重排，不能称为严格扫描模型或已证明的真实完成时间下界。

## 9. 第五步：用同一份输入证明到底哪一部分有作用

新 gem5 把功能角色写入稀疏 `.mreq` 伴随文件，绑定 core、记录序号、微操作成员和源内容校验。不把 gem5 的完成 tick、cache 命中结果或服务延迟喂给 FastSim。热 FST 记录仍为 64 bytes；没有新能力标记的旧输入保持角色未知，不靠 PC 猜测 CDA。

正常采集的新窗口包含 **341,616** 条 NO_ACCESS，每核 **85,404** 条。独立检查确认 CDA 及后续真实 data-store 成员全部保留。用同一新 FST 运行旧模型控制、仅功能修复和组合修复；双方宏指令分母均为 **21,067,990**。

| 模型变体 | gem5 active CPI | FastSim active CPI | 相对误差 | CPI 绝对误差 / 单案 MAE |
|---|---:|---:|---:|---:|
| 旧 timing 模型，仅移植新读取器 | 1.472610 | 1.076678 | -26.89% | 0.395932 |
| 仅 NO_ACCESS 功能修复与本地 SQ，关闭新增扫描估计 | 1.472610 | 1.073441 | -27.11% | 0.399169 |
| 功能修复 + canWB/扫描约束估计 | 1.472610 | 1.342789 | -8.82% | 0.129822 |

绝对误差与 MAE 单位为 cycles/宏指令。三行是同一负载的模型变体，不当作三个独立负载计算总体 MAPE。

这组消融很重要：**只去掉虚假的 CDA cache 请求，并没有改善 CPI。** 组合修复比旧模型增加 5,606,418 active cycles，主要数值变化来自后继 store 的 canWB/扫描约束估计。不过，请求间存在相互影响，这仍不能升级成逐请求独立认证的“纯扫描因果贡献”。

| 目标 elapsed | gem5 | 旧模型控制 | 组合修复 |
|---|---:|---:|---:|
| milliseconds | 2.584096 | 1.889412 | 2.356146 |

实现、协议、测试及原始收据见[修复报告](fst-no-access-repair-20261020.md)和[完成检查](../tmp/noaccess-repair-20261020/completion.json)。后者各项检查均通过。

## 10. 修复时又发现了哪些容易漏掉的错误

不是让最终 CPI 变大就算完成。机制测试和审核还找出了以下问题，并分别修复：

| 问题 | 通俗解释 | 修复后的要求 |
|---|---|---|
| 本地状态只在 audit 开启时跨批次保存 | 开日志与关日志，模拟的机器竟然不同 | 无论是否输出审计，最终接受的状态都保存 |
| 无访存快路径误把纯 CDA 区段当作空闲 | 不去数据仓库，被误认为不占队列、不花时间 | 含 NO_ACCESS 的区段不能走该捷径 |
| 跳过 data event 时也漏了 SQ 槽位 | 人仍排队，模型却把位置抹掉 | 保留空的结构位置，不提供转发数据 |
| 本地旁路绕过序列化清理 | 改了访问类型，却丢了原有排序要求 | 保留 serialize / memory-barrier 的清理 |

回归覆盖真实 Q1/Q64、不同执行路径、audit 开关、缺失/损坏伴随文件、最后一条记录的全流校验、DTLB 与宏/UOP 数量不变。标准生产构建和完整 FastSim 测试通过；输入身份对照 20 项、native validator 13 项、正常 NT 数据与真实坏地址 fault 回归 2 项通过。旧输入的 cycles、elapsed 和 PMU 保持原值。

## 11. 剩余 8.82% 为什么还不能直接归给 DTLB

已经发现生产模型的固定 page-walk 服务与 gem5 经 Ruby 访问 PTE 的路径存在差别。同页 follower 的独立排队、PTE 资源占用、fill 在正确时点可见，都可能影响执行。

但现有 physical-PTE pilot 与 buffer TSO 组合被兼容性检查拒绝。这说明缺的是两套状态如何正确配合，不是缺一个随手开启的开关。删除检查、再增加一个 DTLB，或把固定 walk 延迟调大，都不能自动补齐因果顺序。

后续应分别修复严格扫描准入和 buffer/PTE 的状态兼容性，再用同源控制、机制见证和完整退休账确认作用。当前不把所有剩余误差分配给某一项，也不宣称已经恢复历史 7% 以内的精度。

## 12. CPI 改善了，PMU 为什么还没一起修好

CPI 看整体进度，PMU 还要求每个被计数的事件有正确身份和完整证据。总时间更接近，并不保证各级 miss 数量也接近。

以下为本轮 workload-task 退休 load 事件的原始计数。参考是当前已观察子集，双方仍有 unknown；百分比是 **Incomplete-evidence errors**，不是完整真机 perf 精度。

| 退休事件 | gem5 已观察 | FastSim 估计 | 暂定 APE | gem5 unknown | FastSim unknown |
|---|---:|---:|---:|---:|---:|
| L1 load miss | 585,581 | 714,689 | 22.05% | 237,928 | 549,805 |
| L2 load miss | 154,351 | 177,596 | 15.06% | 362,223 | 549,817 |
| L3 load miss | 29,424 | 45,234 | 53.73% | 362,565 | 550,024 |

unknown 不能当作零，也不能全部当作 miss。这里还缺部分服务成员与 ISA/event 资格证据，错误路径及预取对 cache 状态的间接影响也未完整建模。Ruby tag miss 属于另一类诊断，不能改名替代退休 load miss。

本轮没有新的吞吐测量；全流输入校验和部分快路径回退有宿主成本，尚需同构建、同输入的独立测试。修复结束时 FST 总量约 21.59 GB，低于用户批准的 100 GB 上限。

## 13. 以前是否已经遇到过这个机制

遇到过相关机制，也观察到过 local access，不能把这次问题描述成此前从未出现的新机制。此次补上的，是功能输入与 FastSim 时序之间缺失的连接。

| 既有记录 | 当时已经知道什么 | 尚未证明或补齐什么 |
|---|---|---|
| [9 月 17 日 buffer 设计 §6.5](gem5-spr-tso-store-buffer-design-20260917.md#65-barrier-与特殊访问) | local access、NT 等特殊访问应保守处理，prepare 不跨未完成的 store barrier | 设计约束不证明 FST 已携带请求角色，也不证明 FastSim 已实现本地请求扫描边界 |
| [基线采集文档中的 9 月 20 日 NAMD C8 复验](tso-buffer114-baseline40-collection-20260918.md#62-c8-namd此前修复未覆盖的新-lifecycle-出口) | core4 的 native 无 Ruby 终止分类已经记录 `local_access=10504` | 这是原生观察端的分类，不是逐记录功能输入；不能据此认定全部是 CDA，也未量化其 FastSim CPI 影响 |
| [9 月 23 日普通 store 时序修正 §4](buffer-tso-store-timing-20260923.md#4-尚不能据此宣称什么) | 修正 commit→send、callback、前驱 response→后继 send；明确完整 prepare/demand 协议尚未认证 | 没有补齐 CDA 的 NO_ACCESS 输入身份及其本地扫描限制 |
| [10 月 16 日 NT 调试 trap 修复](spec-rate-sqlite-zstd-collection-20261016.md) | 保留 CDA 和真实 store 的地址、宽度、顺序，去掉非架构调试 trap | 保留指令本身不等于把 NO_ACCESS 身份传给 FastSim |
| [10 月 19 日完整窗口诊断](zstd-cpi-retirement-diagnosis-20261019.md) | 把 NT-copy 大差额、本地请求身份和 gem5 扫描遇 local access 时停止的源码规则关联起来 | 随后才进行本轮 producer/consumer 修复与同源消融 |

因此，之前的缺口是验证没有形成完整闭环：知道存在特殊请求、原生观察器也能分类，但功能 trace 没传身份，FastSim 的普通 store 修复及回归没有覆盖这个组合。之前的“阶段边修正通过”不能解释为整个 store 机制已经完成验证。

这次 Zstd 的密集复制路径让该缺口更容易定位。历史其他负载究竟受影响多大，仍需检查其实际指令组合并做同源对照；不能因为旧 CPI 小，就断言没有触发，也不能直接断言一定被其他误差抵消。

## 14. 以后遇到类似问题，按什么顺序排查

1. **先确认在比同一件事。** 核数、线程、ROI、共同终点、active/elapsed、宏/UOP、硬件参数与参考来源分别核验。
2. **确认参考执行本身合理。** 调试 trap、错误 ROI 等 producer 问题，先修复再重采，不能让 FastSim 模仿它们。
3. **做全窗口、互斥的周期账。** 不把重叠等待相加，不凭 stall 次数大小判断主因。
4. **找具体区段，再找具体动态指令。** 核对日志字段的语义，区分第一次发射、最后重试、数据返回和退休。
5. **区分输入缺语义与模型缺时序。** 输入没有表达 CDA 身份时，单独调整 consumer 很难可靠修复。
6. **用机制测试和同源消融验收。** 检查请求数、队列位置、排序和放行条件，再看 CPI；保留无效尝试和证据缺口。
7. **最后做跨负载回归与吞吐测试。** 一例更准不代表整体更准，也不代表更快。

这次最值得记住的是：**不产生数据访问的指令，仍可能通过队列和先后顺序决定后面的工作能多早开始。** FastSim 既要知道“做了哪些访问”，也要保留“哪些事情必须等前面的步骤完成”。
