## 1. 结论与证据边界

目前最值得优先检查的是：**请求接收受阻后，load 的发射竞争、重试与队列反压是否在同一时间轴上得到一致处理。**

已确认当前 gem5 源码存在请求拒绝后重新进入 FU 调度的路径，Graph500 也有显著的额外 MemRead 发射。FastSim 已经处理接收等待、请求槽位、返回依赖及部分队列反馈，但没有逐次失败尝试的资源语义；默认也没有启用通用的响应侧 FU 重排修复。

尚未确认：额外发射各原因的精确分账、修正后的排程是否实际超额占用端口，以及这类差异能解释多少 CPI 残差。不能将“发现机制差异”写成“全部误差根因已证实”。

| 证据层 | 当前结论 |
|---|---|
| 功能热点 | 本窗口主要是 APSP 标量循环，不是 BFS 原子更新 |
| CPI 误差 | C4/C8 均系统性低估，各核都存在周期缺口 |
| 原生机制 | 拒绝后的 load 能重新进入调度并竞争 FU |
| FastSim 机制 | 有接收等待和队列近似；没有完整逐次重试资源语义 |
| 主要残差来源 | load 接收、发射、队列反压的耦合是强候选，尚未定量证明 |
| 真实硬件等价性 | 未验证；gem5 的三倍发射量不是 SPR 硬件测量 |
| 新设计状态 | 未实施、未验证，不构成新默认或新模型里程碑 |

## 2. 当前诊断摘要

### 2.1 来源、基线和统计口径

- 两例为 `c04-854.graph500_s` 和 `c08-854.graph500_s`。
- 来源分别是 `tmp/spr-no-prefetch-no-early-prepare-c4-20261110/sources/c04-854.graph500_s` 和 `tmp/spr-no-prefetch-no-early-prepare-c8-20261113-parallel/sources/c08-854.graph500_s`。
- 基线为 SPR-M4：功能 TLB 和 UART/APIC 服务开启。
- 已评估 ELF SHA-256：`d6f5bae930dfad9782a938080f1de5e647dc44a6fc967c89dbc6f44e4eb9c5f9`。
- CPI 为 workload-task active cycles / retired macro instructions，终点策略为 `retired-stream-completion-v1`，两侧逐核 task macro 人口一致。
- 结果为 quick 模式，复用保存的独立 BaseCPU task-clock 审计；不是新的严格完整性审计、原生 PMU 准确率认证或硬件认证。

|---|---:|---:|---:|---:|---:|

### 2.2 热点和已降级的解释

两例使用相同 APSP marked ELF，参数为 `-m 19384 -p 16000 -q apsp_NYroad_19384.bin -g 1`。core0 用户 UOP 全部落在 `run_apsp._omp_fn.0`。主循环通常为 7 条宏指令、9 个功能 UOP、3 次 load，条件 store 极少，没有原子 UOP。周期缺口摊到循环上约为 C4 0.89、C8 0.83 周期/轮；这不是发现了一条缺失的固定一拍边。

下列解释优先级已降低：

- **后台 UART：** 两例请求均为 0；全部已记录 IRQ 开销也仅约为残差的 2%，且相应内核流已经执行。
- **TLB 未开启：** 当前功能 TLB 已开启，对本窗口的 CPI 影响较小。
- **大量 miss 遗漏：** 当前保存的 Ruby/SLICC L1D、L2、LLC tag-miss 计数与模型很接近；仍未排除服务延迟、合并、返回和 MLP 的误差。
- **大量分支 miss 遗漏：** 退休分支人口相同，模型 miss 数略多于原生，恢复开关对照没有消除主要残差。
- **原子锁竞争：** 本次功能热点不支持这一解释。

## 3. load 重发的语义

一条退休 load 可以有多次内部执行尝试，最终只退休一次。需要区分：

| 情况 | 含义 | 本方案处理 |
|---|---|---|
| 接收前受阻 | 请求槽、执行资源或访问条件暂不可用 | 显式等待，必要时按事件恢复尝试 |
| 请求已接受但 cache miss | 下层正在取数 | 保持在途状态，等待返回，不自动制造重发 |
| 内存推测错误 | 先执行后发现 store/load 等依赖判断错误 | 首版不凭功能流猜测，标明未覆盖 |
| 错路执行 | 最终未退休的动态指令 | 不生成、不回放 |

真实 CPU 有 load 阻塞和推测失败恢复机制，但具体等待结构、重放方式和资源消耗取决于微架构。当前 gem5 的 BufferFull/retry 接口及其重新经过 FU 的行为，是可复现的模型语义，不是硬件等价性的证明。

参考：[SPR 性能事件](https://perfmon-events.intel.com/platforms/sapphirerapids/core-events/core/)、[Intel 数据推测说明](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/technical-documentation/hardware-behavior-related-to-speculative-execution.html)、[gem5 timing 请求与 retry 协议](https://www.gem5.org/documentation/general_docs/memory_system/)。这些资料分别支持硬件存在阻塞/推测机制和模拟器接口存在接收重试，不能混成一套事件口径。

## 4. 设计约束和选择

推荐采用 **有限队列＋资源日历＋按事件唤醒**，先实现接收与发射安排的一致性，再增加有明确拒绝原因的重试占用。

| 方式 | 取舍与结论 |
|---|---|
| 固定增加 latency、按“三倍发射”增加罚时 | 丢失并行度、双重计费风险高，不采用；固定参数变化只允许作为诊断 |
| 逐次复制 gem5 retry/FU 事件 | 缺少功能流之外的时序信息，容易扩大为详细流水线模型，不采用 |
| 有界事件与批次近似 | 保留请求、资源和依赖关系；适合现有两阶段框架，推荐 |

必须保持：

1. 输入仅为退休功能流及功能伴随，字段能从 Atomic/QEMU 功能执行获得。
2. 不输入 gem5 issue、response、stall、实际 grant、重试次数或命中结果；OoO 只提供独立参考。
3. 不补造错路访存，不增加退休人口；内部失败尝试不生成 cache/DRAM 事务。
4. 不引入逐周期 CPU、独立详细因果运行时或整窗口反复收敛。
5. 高吞吐与精度分别测量；不因某个负载 CPI 改善就默认开启新机制。
6. 目标容量、流水边和服务时间必须有配置或机制来源，不通过修改固定延迟拟合。
7. 适用性依赖功能字段和机制能力；不以整个 gem5 版本或整份策略哈希作为通用使用资格。可执行文件/配置哈希用于实验复现，与逐条字段完整性分开。

## 5. 数据和资源模型

### 5.1 每条 load 的有限状态

```text
功能 load
   │ 依赖、地址翻译、dispatch 下界就绪
   ▼
等待发射 ──获得执行资源──► 尝试接收
                            │
               接受         │         拒绝
                ▼           └──────────► 等待资源事件
            等待数据                         │
                │                    释放／唤醒后重新竞争
                ▼                           │
              完成 ◄────────成功接收─────────┘
                │
              退休
```

每条 load 保留稳定身份、所属核/顺序、片段身份、地址与访问属性、依赖就绪界、首次尝试/接受/返回时刻，以及阻塞原因和资源票据。地址不可用或属性不足时采用明确的旧路径/近似分类并计数，不能删除功能成员或静默猜测 bank。

跨线访问按实际功能片段处理；一次 load 退休与多个 packet 接受/返回分别守恒。转发、NO_ACCESS、软件预取、MMIO、atomic 和 PTE 请求沿用各自路径，首版普通 load 模型不能把它们全部当成缓存读包。

### 5.2 资源生命周期

| 资源 | 分配点 | 释放点／语义 |
|---|---|---|
| 发射槽、AGU/FU | 模型判定实际发生的尝试 | 对应执行资源的预约结束 |
| 请求接收额度 | packet 成功接受 | 对应响应／目标机制规定的 callback |
| 同线下层服务、MSHR | 建立独立 miss 服务 | 服务结束；跟随成员共享服务，不重复取数 |
| IQ | 指令进入相应分区 | 由目标语义决定，不能默认等同于请求槽释放 |
| load queue | 保留该 load 的状态 | 按目标模型的完成/退休生命周期处理 |
| 重试等待项 | 尝试受阻且需要保留 | 成功接收或转入其他合法状态；可附着在已有 load 上 |

同线服务身份与成员接收额度必须分开：合并一次下层服务不等于成员免费接收；也不能对同一成员同时重复占用两个表示相同物理容量的队列。

模型配置需明确生命周期来源是“当前 gem5 对齐”还是“有硬件证据的近似”。首版不能因 gem5 持有 load IQ 至返回，就宣称真实 SPR 必然同样处理。

### 5.3 按事件计算接收和重试

普通 load 的最早尝试时间由 dispatch、功能依赖和翻译下界共同约束。资源日历寻找可用的发射位置，随后按目标接收规则判断请求是否能接受。

- 条件已经在发射前阻止尝试：只计等待及相应队列占用。
- 模型明确表示已经尝试、随后拒绝：计一次失败尝试占用，挂到具体阻塞原因。
- 已接受：分配请求额度并接入已有下层服务，等待返回。

槽位满时，下一次可能恢复的时刻由模型已有的释放事件推导。等待者按稳定顺序和真实可用额度分批恢复；唤醒不保证全部请求立即接受，成功尝试仍受发射带宽和剩余额度限制。独立就绪指令在资源允许时继续执行；一个受阻 load 不应自动暂停整核或全部核心。

失败尝试、等待、成功尝试和数据服务分别记录。接收受阻的等待已经计入时间轴后，不能再按 retry 次数追加相同等待。

## 6. 与现有两阶段框架的衔接

### 6.1 第一阶段：并行产生下界和功能描述

继续沿用每核 trace、前端、依赖和 IntervalCore 批次生成。补充稳定的 load/片段身份、资源类型和必要的功能就绪信息。第一阶段时刻仍为模型下界，不称为原生实际时刻。

### 6.2 第二阶段：一次有界资源反馈

沿用共享事件提交和响应反馈，在现有接收槽/返回日历附近修正资源安排：

1. 确定队列允许进入和依赖就绪的最早时间。
2. 处理受阻事件、释放事件及可唤醒批次。
3. 为实际尝试登记执行资源预约，成功接受后登记请求额度。
4. 返回完成更新依赖、队列释放和退休下界。
5. 只前推受影响的本地依赖及资源安排，不进行整窗口反复重算。

第一阶段已有预约与第二阶段新预约需要明确的所有权/代次规则。移动后的预约必须替换旧预约，或由新的资源日历明确接管；不能同时保留两份收费，也不能只移动 completion 而漏掉同周期竞争。首版优先审计这一点。

### 6.3 共享顺序的近似边界

本地修正会改变请求就绪时刻，而共享 cache/DRAM 服务可能已经按本窗口既定顺序提交。首版保留既有一次提交顺序，不增加回滚、重新分类和整窗口收敛。

这一边界应显式计数：实际就绪比已提交服务起点晚的事件、偏移量、受影响片段及窗口边界延续情况。服务尚未满足接收条件时不能提前完成；必要时采用明确的前向下界修正，但不能称其为重新计算后的真实共享排队结果。跨核请求到达顺序和行命中等残余近似应单独报告。

## 7. 高吞吐实现原则

- 每核维护资源规模有界的日历、等待摘要和释放事件；不把所有 UOP 放进新的全局事件堆。
- 直接跳到下一次释放/就绪事件，不逐周期轮询。
- 连续且条件相同的请求按批次处理；按本次可发射数量与可用接收额度计算推进。
- 状态跨 chunk/epoch 保留，warmup→measurement 的转移不能清空仍在途的服务或额度。
- 容量达到上限时通过推进释放和输入反压处理，不能丢弃请求、无限扩容或静默忽略重试。
- 提交、复制、撤销或回退时同步处理资源票据；避免失效 ready time、重复释放和悬空身份。

性能目标是让工作量主要随退休功能事件、必要释放事件和有限批次变化，而不是随目标周期数变化。具体开销尚未测量，不能预先宣称达到吞吐门槛。资源查找若仍存在逐周期扫描，应在该机制评估前替换为区间跳转或其他有界查询。

现有 `SparseIssueResourceCalendar` 可作为接口参考，但包含容量冲突时逐周期推进的实现；也不是 SPR 所有共享端口语义的通用实现。不能直接开启 `response_sparse_resource_repair` 当作本设计完成，该旧实验路径与当前 v2-wait 等约束存在冲突。

## 8. 分阶段实施与交付

| 阶段 | 工作 | 交付和继续条件 |

| P0：证据和守恒审计 | 分开首次尝试、各原因重试、成功接受、返回；审计修正后端口预约与队列释放 | 确认真实违规或可复现的机制差异；统计模式需与默认预测一致 |
| P1：接收与发射一致性 | 修正移位后的 load/相关执行资源安排，处理预约所有权和跨窗口状态 | 资源约束与人口守恒成立；此阶段不引入经验重试倍数 |
| P2：事件聚合重试 | 对明确拒绝原因增加失败尝试与释放事件唤醒，按有界批次恢复 | 拒绝原因、资源占用与等待分开；已接受 miss 不制造额外尝试 |
| P3：多负载评估 | Graph500、Zstd、XZ、FLAC、Marian 的现有 C4/C8 输入，同源默认/候选配对 | 完整报告改善、恶化、不可用项及独立吞吐；按证据决定是否保留候选 |

P0 可以发现“主要差异不是重试”或“没有端口超额安排”。若如此，应更新诊断并调整 P1/P2，不能为了完成预设方案强行补费。

新机制初始为独立 opt-in 候选，关闭时保留现有路径。具体配置名称尚未确定；不改动不可变 M1–M4 profile，不把本设计自动命名为 M5。默认切换、里程碑推进和数值验收门槛属于后续明确决策。

## 9. 验证与报告方案

### 9.1 必要的机制检查

| 检查 | 要证明的行为 |
|---|---|
| 无阻塞命中 | 不凭空生成失败尝试，不重复增加 latency |
| 请求槽满 | 等到释放事件，唤醒数受接收额度和发射带宽约束 |
| 同线跟随 | 多个成员共享服务，成员额度和服务身份分别守恒 |
| 延迟返回与后续依赖 | 依赖不能早于合法返回就绪，独立指令仍可推进 |
| 同时唤醒与端口争用 | load/ALU/branch 的实际预约满足各自可用端口和共享限制 |
| 跨 chunk/测量边界 | 在途状态保留，既不提前释放也不重复分配 |
| 转发、跨线和特殊访问 | 按各自 packet/退休单位处理，未支持字段明确保留旧路径或 unavailable |

逐成员记录 `attempts = first_attempts + retries`，成功接受不超过该片段需要的合法次数。数据服务另行守恒；发射重试不增加退休指令，也不自动增加 memory read transactions。

### 9.2 诊断计数和语义

建议新增或明确以下统计，名称为设计建议，尚非已实现接口：

- 普通 load 首次尝试、成功接受、被拒绝、按原因重试。
- 未尝试的接收前等待、尝试后的阻塞等待、唤醒批次大小。
- 修正后预约的冲突数、移动次数、最大偏移和重复预约检查。
- 请求成员、同线服务、在途额度和队列占用的峰值/守恒。
- 共享到达时刻近似、缺失字段、特殊访问和回退覆盖。

资源累计等待、占用周期和 FU busy 次数可能重叠，不能加成 CPI。首次 issue、成功 admission、response、producer ready、retire 的时间起点分别标注；不同起点的平均延迟不能直接算误差倍率。

### 9.3 精度评估

默认采用维护入口的 quick 模式，比较同来源、同逐核人口、同 warmup/measurement 边界和同退休终点。使用 `--source-root` 与 `--stats-dir` 重评分，避免临时脚本重选 CPI 参考。

每负载给出 gem5 CPI、默认/候选 CPI、相对误差、CPI 绝对误差；聚合报告等权 MAPE 和 CPI MAE，WAPE 单独列出。保留 Marian 和所有恶化项，同时可以另列不含 Marian 的视图。

quick 不能产生新的严格 PMU 认证。缓存原生参考只接受经维护审计流程约束的 Ruby/SLICC 来源；缺失证据为 unavailable，不能用 `kernel_events` path-class 字段替代。

### 9.4 吞吐评估

独立使用 `scripts/run_high_frequency.py` 绑定 CPU 52–63，记录实际频率、ELF 和有效配置。默认/候选用相同输入配对，不用并发准确性回放的 wall time 宣称吞吐收益。

按 2026-11-16 最新用户口径，主吞吐分母计入输入读取、预处理、初始化、功能 warmup、模拟和必要排空；重复可靠性审计独立计时。使用维护的 `e2e_launch.py`、未变输入收据和原始 FST 回放，记录全局 monotonic 起止时刻；`HOST_VALIDATED_PRELOAD=true` 的 measurement-only 速率仅作辅助，不从线程 CPU 时间推算校验排除量。见 [端到端吞吐合同](trace-comparison-throughput-contract-20261116.md)。

本方案尚未约定新的数值吞吐损失阈值或全负载精度通过门槛，因此完成测试或单个案例改善都不能自行标为“验收通过”。
