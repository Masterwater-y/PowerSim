# 关键请求覆盖验证：普通 store 与资源组回退

日期：2026-09-10。**两项机制已实施并通过测试，但没有达到关键路径修复目标；
CPI 与吞吐验收均失败。候选保持默认关闭，不推广、不扩大验证矩阵。**

本轮承接 [上一轮共享服务候选](shared-service-arrival-phase2-20260910.md)。
保留 `interval_weave + time_epoch`、Q=1024、并行 producer、共享批处理和并行
materialized feedback。未启用 causal_read，未改变 DRAM 参数、FST、gem5 reference、
ROI 或设备范围，没有使用 PC/负载分支或补偿系数。

## 1. 先检查原关键请求为何没有进入修复

复用 [完整 ROI 审计](tealeaf-full-roi-error-audit-20260910.md) 的 20 个 DRAM load
头见证，在隔离诊断副本中记录资源组、访问核心、普通 store 和拒绝原因。诊断运行的
CPI、scope PMU、全部共享服务计数与上一轮最终候选完全一致。

- 7 个见证所在的资源组没有跨核冲突，但普通 store 导致整个组被排除。
- 另外 13 个同时具有跨核冲突和不支持的请求，不能只去掉 store 限制。
- 这 20 个见证所在批次均未触发隐藏 DRAM 副作用排除。

这比按全局计数猜测覆盖更明确。`origin == actual_issue` 或 latency 改变都不能
单独证明请求使用了候选服务。本轮增加隔离的最终提交记录，以直接验证是否接入。
所有按 sequence 选择见证的代码仅位于 `tmp/` 诊断副本，不进入生产模型。

## 2. 实施的两项通用机制

### 普通 store 在提交后进入共享服务

普通 store 的冷行获取会使用 DRAM read 资源。它与 LLC dirty writeback 的生命周期
不同，不能把 store 当成后者，也不能在地址生成时预约其共享请求。

对于通过原资源/路径检查的普通单片 store：

1. 地址生成阶段保留核心依赖计算，延后请求容量与共享服务预约。
2. 使用已有 gem5 O3 阶段定义，在 `retire + 2`、TSO 前一 store 的 `response + 1`、
   请求自身起点，以及 Sequencer/private MSHR 下界都满足后准入。
3. 在同一次核心反馈中重新计算 CHA、LLC MSHR、DRAM 服务；响应驱动 SQ 释放和
   后续 TSO store。store 自身退休不等待这次普通写请求的响应。
4. 导出的 fragment 请求时刻必须与产生共享服务的时刻完全相同；失败时恢复旧结果。

这里的 2/1 cycles 来自仓库既有 O3 store 状态转换定义，不按 TeaLeaf CPI 选择。
split store、atomic、PTE、权限升级、远端供应、取指、carried 请求以及未覆盖的
副作用仍保持排除。没有新增 dirty writeback；本轮两端 DRAM writes 均为 0。

### 回退保留独立的合法资源组

上一轮静态检查已分组，但进入核心反馈后，各独立组又共用一个候选工作块。
任意组的末尾请求越过未来请求下界，会使整块的合法服务一起回退。

本轮保留 CHA/channel/LLC replacement set 的连接分组。越界时只移除相应完整资源组，
从原入口状态恢复该核心，并只启用剩余组重新反馈。随后重新检查所有核心的出口下界，
防止恢复后的时刻变化使其他组失效；没有放宽原边界，也没有固定迭代次数后强行接受。
每次重试至少移除一个资源组，最终不稳定的核心恢复旧模型。

资源状态、响应、队列统计和核心反馈在最终验证后一起提交。失败组没有部分日历泄漏。
仍然从 **epoch-entry 到 accepted-prefix 出口** 恢复核心，尚无任意中点恢复能力；
本轮不能称为低成本的局部核心修复。

## 4. 验证与停止决定

- 普通 store 的提交后请求与 TSO/SQ 反例在旧代码明确失败；独立资源被连带回退的
  反例也在修复前明确失败。修复后通过，generic/materialized 一致。
- `cmake --build build -- -j16` 与完整 `./build/fastsim_tests` 通过。
- 现有 RAW、WB、跨 epoch DRAM 状态、顺序/可见性回退测试继续通过。
- 2 次定位诊断、2 次实现阶段完整 ROI pilot、1 次完整阶段导出、4 次 ABBA、1 次
  默认关闭对照，共 10 次 FastSim；无新 gem5、FST 重采或其他负载矩阵。

**不将这轮作为 CPI 改善合入默认配置。** 保留候选和反例供后续机制工作复用。
本轮没有达到此前设定的“已知关键请求进入修复、阶段差异缩小、退休缺口下降”条件。

下一步不能继续仅扩大 eligibility 或增加等待。关键阻断要求在现有两阶段框架内补充：

1. 核心 accepted prefix 的中点状态保存与恢复，覆盖 RAW/WB/dispatch/ROB/LQ/SQ、
   退休和 store send；恢复范围不能默认扩成整个核心 prefix。
2. 尚未达到准入条件的共享请求跨 Q 保留身份，待其他核心的早到请求进入后共同求解；
   在新的请求集合下验证服务顺序及 cache/fill 路径，并只提交一次。
3. 先用原关键请求检查该流程确实运行，再对正确到达流检查控制器命令和 refresh。

单独删除边界检查、强制保持旧队列等待、改 Q 或启用额外全 UOP 固定点迭代均不作为替代。
下一次运行前先读取本报告，避免把本轮失败候选当成已经完成主导误差修复。
