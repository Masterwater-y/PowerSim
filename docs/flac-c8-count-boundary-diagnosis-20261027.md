# FLAC C8 指令计数差异：共同终点落在syscall内部

本轮FR-FCFS对照复用了2026-10-22的旧10M来源。该来源在2026-10-23的维护验证中就已报告同样的差异；并非开启FR-FCFS后新出现。另有2026-10-26重新采集的2M来源通过了完整检查。两份数据窗口不同，必须分别标识。本轮没有优先核对后来已通过检查的来源，样本选择和说明需要纠正；不把后来的通过状态套到旧FST上。

## 具体差异

旧来源core0/线程1621的测量区间，FST记录7,881,021条，包含16个折叠syscall标记。当前检查将每个标记按完整25个微操作展开，即增加24条，得到7,881,405；gem5实际统计为7,881,399，相差6条。宏指令和分支分别相差1条，访存微操作数相同。

最后一条FST记录为ordinal20,296,581，PC `0x462682`，op_class=-1，syscall编号0。原FLAC ELF反汇编确认它是`__libc_read`中的`syscall`。本窗口由core5达到目标触发共同结束，core0自己的syscall尚在进行。

采集器在syscall第一条微操作提交时输出折叠标记；gem5按实际提交的微操作逐条计数，宏指令到最后一条微操作才计完成。FST检查却将这个尾部标记当成已经完整执行的25条。因此该边界会把尚未完成的部分也计算进去。按照整体计数反算，最后一次调用计入19条而非25条；19这一数值是由总量差和尾部记录推导，不是已有原生逐微操作时序日志的直接观测。

这解释了6条微操作、1条宏指令和1个分支的差额。旧、新DRAM模式都复现同一错误；调度开关不会改写FST或gem5原始统计。

## 为什么之前看起来没有问题

- 同一旧10M来源并未通过详细检查：`tmp/spec-c8-accuracy-20261022/validation/legacy-prepare/flac/cases/c08-817.flac_s/validation.json`于2026-10-23已保存相同错误。`source-ready.json`的采集完成标记不能替代该详细检查。
- 后来的合格结果属于另一份2M来源：`tmp/spr-retired-zero-unknown-20261026/implementation/second-producer/source/c08-817.flac_s`，维护结果在`implementation/final-two-case/validation/cases/c08-817.flac_s/validation.json`。
- 新窗口检查通过，不证明旧文件已修复，也不能仅凭换窗口认定该类syscall截断边界已彻底修复。采集端仍需完整表达末尾未完成的系统调用，检查端按实际完成部分计数。

未改写旧FST、原始参考计数或此前不合格状态。本次只定位原因和澄清来源版本，尚未修改采集器或执行新的重采。后续新实验应优先使用已通过检查的来源，并明确2M/10M窗口差异。

证据：`tmp/flac-count-boundary-20261027/evidence.json`及同目录反汇编。实现依据：`TaoTrace::isSyscallBoundary`仅接受first micro-op，`accountTaskPmuCommit`按last micro-op计算宏指令；`tools/audit_task_pmu.py::functional_populations`对每个syscall标记增加24个微操作和1个分支。

## 已知问题与暂缓修复（2026-10-27）

用户要求先记录问题、暂不修改实现，并在本次报告中忽略这项极小计数差异。因此下列事项均为待处理项，不代表已经修复。

| 问题 | 当前证据或风险 | 后续处理方向（本次不实施） |
|---|---|---|
| syscall标记早于指令完整提交 | 入口微操作输出折叠标记，共同终点可落在指令内部；旧FLAC尾部已复现 | 优先保存实际提交的微操作，入口参数作为附加信息；或给折叠记录增加实际完成前缀及宏指令是否完整提交的信息，并使模型按该前缀执行 |
| 完整展开规则无法表示部分提交 | 当前检查把标记固定展开为25条微操作，并计1条完整宏指令及分支 | 同步检查采集器、转换器、读取器、模型和核对工具，按实际完成部分计数；不能只修改核对数字而保留完整指令执行 |
| 其他边界尚未系统覆盖 | 本次直接证据是测量末尾；测量开始、预热切换及其他部分宏指令边界仍需专项核对，不能推定都存在同样错误 | 补充首条、中间、末条前、完整提交及跨预热边界用例；区分部分微操作工作量与完整宏指令退休 |
| 采集完成与详细检查状态混淆 | source-ready有效，但同一旧来源早在10月23日就详细检查失败 | 来源清单同时记录采集完成、逐核/线程指令计数核对和参考事件覆盖，不用单个完成标记概括全部状态 |
| 新旧窗口选择与说明不足 | 本轮使用旧10M来源，另有已通过检查的2M来源 | 在选源时列明采集版本、窗口和检查状态；明确选择后再比较，不静默替换或混合两份数据 |

共同终点继续保持原定义，不能为了等待syscall完成而延后，也不能删除尾部实际已执行的微操作。这里的“完成”指SYSCALL指令的最后一条微操作提交，不是等待read内核服务返回。若后续调整格式，需要版本/能力标识及旧格式兼容策略；旧数据缺少实际前缀证据时不能把反推的19条写回当作实测事实。

本次例外只适用于上述FLAC的CPI暂定展示，未建立全局容差规则；FST、gem5计数、原检查结果均保留。含FLAC的三负载对照、MAPE/MAE及仍未解决的PMU限制见[暂定结果报告](frfcfs-c8-provisional-results-20261027.md)。
