# Marian C4 store 准备与窗口诊断

## 范围

本次使用原 Marian C4 FST、user-plus-kernel 范围和当前配置，对同一二进制分别关闭和开启诊断。诊断不改变调度，功能来源、计时、各核指标、总计与预取指标一致。原有同采集对照中 FastSim CPI 为 2.759166，gem5 CPI 为 1.428304，绝对误差 1.330861 cycles/macro instruction，相对误差 +93.18%；两者窗口并非严格同成员对齐。数字不是诊断代码的性能测试。

## 结果

- 2,256,928 个 direct 中，1,663,869 个到自身允许时刻时就已发送；593,059 个受前序扫描边界影响。按同一事件发送时刻比较，新旧公式对 direct 的额外服务周期为零；这不是完整运行级开关对照。
- 4,656,846 次窗口请求中，仅 890 次由四行容量直接阻塞，累计 30,199 个等待周期。原先以四行窗口满为主要解释的说法不成立。
- 2,149,208 次窗口请求首先归因到 barrier，其中 2,137,497 次是 local NoAccess 继承前序 store 排空边界。当前模型让 NoAccess 等待前序 drain，再把自己的释放时刻传播给后续扫描和窗口；NoAccess 本身不请求缓存数据，也不是 ISA fence。
- 分类账中的 barrier 等待共 4,134,009,713 周期，但后续请求的等待相互重叠，也与已有发送顺序重叠，不能当作 CPI 损失。在保持既有窗口和发送状态不变、仅对当前事件忽略 barrier 的局部反事实中，1,019,009 次请求合计改变 57,456,394 周期；不是整个运行移除 barrier 的收益。
- 对继承边界的来源按被阻塞请求重复加权：代表性前序为 local 路径的 1,660,804 次，发送前排队平均约 1,871 周期，发送后至释放平均约 2.43 周期；memory 路径 460,119 次，分别约 2,213 和 240 周期。这说明 local 标签不意味着本地缓存服务本身用了上千周期。来源可能被多个后续请求重复引用，时间相同的来源选择一个代表，不能视为独立样本。

## gem5 与 FastSim 的准备时机

本次 gem5 四核配置均设置 `sprEarlyStorePrepare=true`、`cacheStorePorts=2`、`tsoOrderedStoreLineWindow=4`。gem5 允许合适的、已获得地址的 store 在 `canWB` 前发送 prepare，但遇到 local access、顺序操作等条件时扫描仍会停止。本次完整统计中 prepare 发出 2,355,146 次，其中退休前 2,354,733 次；这包含推测路径和完整统计区间，与 FastSim 退休流不是可直接相减的同一总体。

当前 FastSim 近似把准备候选时刻设为 store 自身退休后 admission 与 local 扫描边界的较大值，因此缺少 gem5 已退休指令在退休前的准备提前量。它是值得继续验证的时间轴差异，但现有证据不能定量确定其在 CPI 误差中的份额。后续如近似提前，应只使用退休功能流可获得的信息，不能引入 gem5 OoO 时间戳或猜测错误路径流量。
