# FLAC C4 CPI 差距：同源消融与计时证据

状态：执行中。目标是解释 gem5-spr 基线与 FastSim 的差距，不修改负载、
原始 FST、SPR 配置或将 gem5 OoO 的动态时间用于 FastSim 输入。保留
现有并行两阶段与一次反馈。每个消融使用同一 FLAC C4 采集、manifest、
thread-state 计划和冻结二进制；输入内容身份通过正式 consumer 输出。

## 已确认的对照和计时边界

同批已有合格 task 人口的对照（共同来源、共同任务及逐核退休人口验证，
起点严格对应尚未证明）：gem5 0.282346215、FastSim 基线 0.500305493，
绝对误差 0.217959277 cycles/宏指令、相对 +77.20%；store 窗口与 fill
同时开启为 0.489617558，绝对误差 0.207271343、相对 +73.41%。
正式 validator 的 passed 是来源及人口门禁，不是准确率合格或硬件认证。

实际读取 `prepare_measurement_phase()`：FastSim 先回放所有核的预热前缀，
将各核模型时间推进到所有前缀结束的最大时刻，再统一开始测量；不是各核
各自独立开启统计。gem5 的四核 ROI begin tick 均为 52398720281600；
各核 warmup cut 分别为 841026、710135、693335、1206592 条记录。两者
是否为相同功能时刻尚无完整退休锚证明。不得把误差全部解释成起点问题。

当前 native task-clock oracle 有共同 BEGIN 的 active counter 和此前已知的
任务切入快照，但没有逐核最后一条 warmup 退休时刻。对每核，最后一次
已知任务切入快照的记录序号严格小于 warmup cut，该任务在 BEGIN 时仍为
相同、已知且 active 的目标任务。last-warmup-retirement 到 BEGIN 的
native 活跃周期，因而不超过该快照到 BEGIN 的活跃周期：

| 核 | 切入快照 ordinal | warmup cut | 活跃周期粗上界 |
|---|---:|---:|---:|
| 0 | 202851 | 841026 | 405645 |
| 1 | 232076 | 710135 | 225763 |
| 2 | 57221 | 693335 | 416926 |
| 3 | 47446 | 1206592 | 396464 |

合计 1444798 cycles，以本次 31226613 个任务宏指令为分母为 0.046268
cycles/宏指令。这**只是原生 warmup 末退休到 BEGIN 的粗上界**，不是该
段实际开销，也不是模型屏障效应或总 CPI 误差上界，更不能直接用来调整
参考 CPI。证据、假设及来源 SHA 见
`tmp/spr-cpi-ablation-20261105/warmup-tail-bound.json`；该诊断只读 OoO
baseline，未进入输入流。

## 消融设计

- `base`：SPR 退休流前端＋分区 IQ；实验 fill 和 store 窗口关闭。
- `iq-off`：只关闭分区 IQ，回到合并容量代理。
- `fill-only`：在 base 上只开启 16/48 普通 load fill 近似。
- `store-only`：在 base 上只开启四行 store 并发近似。
- `combined`：同时开启 fill 和 store 窗口。
- `frontend-off`：在 base 上只关闭 SPR 退休流前端，切换至原有前端；这是
  敏感性对照，并非正确的 SPR 配置或真实硬件前端。
- `attribution`：在 base 上开启现有 CPI 归因并关闭优化执行核；必须先
  比对普通 base 的任务与逐核人口、源身份、CPI 等目标结果，证明无变化
  才能解释归因。归因周期为模型定义的分解，不等于 gem5 的真实停顿。

并发实验不作为性能结论。每个结果保留独立配置、日志和输入内容身份；
所有比较的基准相同，只以退休流和功能属性生成模型事件，不使用原生
错路径、预取结果或 issue/response 时刻。

## 第二阶段反馈增量的诊断

同一来源、同一任务及逐核人口下，开启 `sim.cpi_attribution` 并使用通用
response kernel 后，各核活跃周期与 base 完全一致（四核分别 3605472、
4071544、3927912、4017918）。归因报告 `response_critical_total_cycles`
为 593817，分解为 dependency 382697、memory response 117677、SQ capacity
92812、instruction fetch 631，合计守恒。此计数由现有代码对第二阶段
`exposed_extra_cycles` 归因，并非整个模型周期或模型与 gem5 的差值。
不能据此说“77%误差中多少百分比来自依赖”；它只能说明下一步应检查哪些
反馈路径、以及占总模型时间的大部分并不在这个响应增量账本中。

store-only 相对 base 减少的 333748 个活跃周期中，core0/1/2/3 分别减少
230972/12122/90414/240。base 的 `o3_tso_store_stall_cycles` 为 91448088，
store-only 为 24718657；此类资源等待是事件累计，多个 UOP 的等待区间可以
重叠，不是墙钟周期或 CPI 差距，不能用计数差除以指令数当收益。

进一步执行 `store-set-off`、`forward-off`、`shared-fu-off` 三个与 base

## 从原生和源码发现的新高人口缺口

这两项是机制证据与优先级线索，不是 CPI 归因：

1. 在该 C4 采集的 `stats.txt`（原生物理核 ROI 统计）中，四核
   `moveElimination.retired` 为 259446、1170897、1053485、1121389，
   合计 **3605217**；`zeroIdiom.retired` 合计 **173171**。这些属于原生
   物理核统计，不能直接冒充 task 口径或带入 FastSim。gem5 源码
   `rename.cc` 使用静态整宽 GPR/XMM 类型、操作数及模拟中的 pinned 状态
   判断 MOV 消除；`iew.cc` 对消除的 MOV 不入 IQ，目标映射到源的 producer。
   zero idiom 的目标生成由 `zero_idiom.cc` 完成并绕过正常 IQ 路径。
2. 静态功能束中的 `kCoreFullGprMove/kCoreFullXmmMove` 当前只在
   `fst_core_functional_reader.cpp` 覆盖率统计使用，没有在现有两阶段
   `interval_core.cpp` / `simulator.cpp` 中消费并建模 rename alias；
   `.uops.gz` 的 `zero_idiom` 描述同样未被这两处执行路径消费。完整源
   包括预热的静态 MOV 候选数为 GPR 660804、XMM 3189317，来自已准备的
   `spr-capture-preparation.json`。静态候选、原生实际消除和 task 人口是
   不同集合，不可相减或声称完全对应。
3. 原生同窗口 stats 的四核 `commit.committedInstType_0::total` 合计
   34907951、`UOPS_RETIRED.SLOTS` 合计 31124881。原生将共享分配组按
   槽计数；FastSim `IntervalCoreModel::allocate_retire()` 每条记录增加
   一次 `retires_this_cycle_`，第二阶段也对每条 UOP 增加 commit 使用量。
   原生 stats 和 FST common-end 人口边界略有差异，这两个总数不能直接
   拿来做 model/native 误差；但证明共享分配的目标人口不可忽略。

后续应优先验证退休流可获得的静态 MOV / zero-idiom / allocation-group
资格，采用模型自己的依赖和资源状态决定别名及就绪，未知时显式回退。
不能将 gem5 的 `eliminatedMove`、物理寄存器、ready 时间或实际融合结果
放入 FST。设计应同时保证带源未就绪的 MOV 使下游等待源 producer，并在
两阶段一致保留 ROB、提交槽、跨 chunk 依赖；必须以功能 producer 的
Atomic/QEMU 等价性为前提。这些机制对 CPI 的贡献仍未消融和验证。

## 已发现共享 FU 开关混合多个变化

只关闭 `core.spr_shared_fu`：相同源、任务、人口、可执行文件的 FastSim
CPI 由 0.500305493 降至 0.295847167，变化 −0.204458325；参考 gem5
CPI 为 0.282346215，绝对误差 0.013500952、相对 +4.78%。该对照只是
敏感性实验：关闭后使用通用 FU，并非 SPR 行为，不能当成修复或验收。

检查 `IntervalCoreModel` 可知开关同时影响两类东西：1）SPR 12 端口的
共享占用／仲裁与通用独立 FU pool 的区别；2）若干 OpClass 的延迟和
pipelining 覆盖。不能把 −0.20446 CPI 直接归因于端口拥塞。
尤其 source gem5 `FuncUnit.py` 的 SPR 编号在 FST 读取时会转换为 FastSim
内部 legacy 编号：原生 `SimdMult` 21 对应内部 18；原生
`SimdFloatMult` 34 对应内部 31。实际 gem5 配置分别为 3、4 周期；
共享开时模型覆盖为 3、4，关闭后都回到通用 `core.simd_latency=1`。
原生物理核 `stats.txt` 的已提交类别分别为 3297032、834517；该物理核
stats 范围与任务 FST 不完全等同，计数不作为 task 精确人口或 CPI 归因。
不能直接按原生枚举编号查内部 `spr_port_mask` 并据此判断端口不匹配。

新增默认关闭的 `core.spr_shared_fu_generic_latency` 仅用于诊断：保持
SPR 共享端口，跳过 SPR 延迟表覆盖。要与同一新二进制的 base 和
shared-FU-off 对照，才能区分“延迟表＋pipelining”与“端口/仲裁模型”
的敏感性；通用 1-cycle 并非 gem5 参数，实验不可升为生产配置。

三项同源单开关诊断已完成，task/逐核宏与退休 UOP 人口、输入身份均匹配：

| 关闭同 PC store-set feedback | 0.501646945 | +0.001341452 | 0.219300729 | +77.67% |
| 关闭 store forwarding | 0.500192640 | −0.000112852 | 0.217846425 | +77.16% |

理解为这些机制可安全删除。上述共享 FU 结果同时改变端口及操作延迟，

## SPR 共享 FU 未来预约错误：局部修复方案

最小重现：三条退休流 UOP 都需要 SPR 端口 1；第 1 条是高延迟 producer，
第 2 条依赖第 1 条，因而在未来周期预约端口；第 3 条独立，本可在第 2 条
之前的空档发射。当前 `spr_port_ready_[1]` 保存未来预约的最晚结束时刻，
致使第 3 条被错误地推迟到第 2 条之后。构造回归已在现代码上失败；这不
需要错路径或 native issue 时间。

在原有 `IntervalCoreModel::allocate_issue` 中增加默认关闭的 SPR 共享端口
区间预约路径。每个物理端口只存尚未安全丢弃的已预约半开区间；高 issue
interval 的 `(port, OpClass)` 独立保存同类预约区间。一次 UOP 按已有宽度、
load/store 端口、store data 配对及端口能力寻找首个可用区间，插入该模型
自己的预约；不改变第二阶段、创建 CA 执行循环或对整窗迭代。保留原有
固定端口搜索顺序，轮询仲裁单独验证，避免把两个因素混为一次修复。

使用按起点排序且可回收前缀的紧凑区间向量，按单调 dispatch 下界回收旧
项；允许后来处理的 UOP 填入早于未来预约的空档，并检查整个非流水化
占用区间以及后续同类发射间隔，不能与已预约未来事件重叠。特例覆盖
store 数据端口配对、跨 chunk 状态、同周期竞争和不同 latency/II。区间
只保留活跃预约，不生成未来指令或错误路径。保留旧路径与诊断计数以供
OFF/ON；完整单测后，用同二进制、同一 FST 比较正确性、CPI 和吞吐；
只有通过结果与性能验证才考虑启用默认路径。

三组已用**同一新增诊断开关的冻结二进制**及同一输入完成，来源身份、
任务与逐核宏/UOP 人口匹配。模型参考仍使用前述 gem5 CPI 0.282346215：

| 模型配置 | FastSim CPI | CPI绝对误差 | 相对误差 |
|---|---:|---:|---:|
| SPR共享端口＋SPR延迟（基线） | 0.500305493 | 0.217959277 | +77.20% |
| SPR共享端口＋通用延迟表 | 0.388803743 | 0.106457527 | +37.70% |
| 通用独立 FU 池＋通用延迟表 | 0.295847167 | 0.013500952 | +4.78% |

对这条消融顺序，保持共享端口时切换延迟表/pipelining 使 CPI 减少
0.111501750；保持通用延迟表再切换 FU 资源模型减少 0.092956575。
非线性和资源交互仍在；这不是严格的误差分摊，也不说明通用延迟或独立
FU 符合 gem5-spr。具体如 `SimdMult` 目标延迟 3、通用 1，直接采用通用
延迟会违背参数对齐。原生目标可用 rename move/zero-idiom 旁路、共享组
与不同的端口调度/转发，当前模型尚不完整，需继续分别验证。

构造测试额外复现了一条独立的共享端口错误：未来预约屏蔽了更早的空档。
它可能影响 FU 资源模型敏感性，但其对 FLAC CPI 的贡献仍须实验量化，
不能将整个 0.09296 或 0.20446 CPI 直接归因于这一错误。

### 共享端口空档修复：真实 FLAC C4 同二进制验证

使用同一 `fastsim-gap` 冻结二进制、同一 manifest、功能伴随和 task 计划；
开关唯一变化为 `core.spr_shared_fu_gap_aware`。两侧输入内容身份与已审计
native reference 相同，task ID、逐核退休宏和 UOP 人口一致。使用现有
`time_accounting.build_time_comparison` 和 `retired_cache_contract` 复核；
正式维护 validator 的 `--source-root/--stats-dir` 复评分支正在运行。计时
起点仍按本文的非严格诊断边界解释。

| 配置 | gem5 CPI | FastSim CPI | CPI绝对误差 | 相对误差 |
|---|---:|---:|---:|---:|
| gap OFF | 0.282346215 | 0.500305493 | 0.217959277 | +77.20% |
