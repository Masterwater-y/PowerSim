# 可选 rank 刷新机制与两案验证（2026-11-03）

已完成实现、机制对照、CPI/PMU评分与三轮顺序配对吞吐测量。旧路径目标统计
逐位不变；刷新边界验证通过，但R-only使两案CPI MAE变差，G500平均吞吐损失
略超过3%，两案均出现单对越线。**默认保持关闭，不推广为精度或吞吐已验收的配置。**

## 实施范围

新增 `dram.refresh_enabled`，**默认false**，不修改任何默认profile。关闭时保留旧
目标路径；开启时在当前compact DramModel中处理rank刷新，沿用两阶段分类和稀疏
前向反馈，不增加全局核心/内存迭代，也不提高已有FR-FCFS求解次数上限。

本轮仅Marian C4、G500 C16的user-plus-kernel冻结P1前缀；不代表六项或全矩阵验收。
没有修改gem5 runner、重采FST、拟合参数、commit或push。

## 选项与机制

当前采集配置的启用示例（其他配置必须从各自config.json导入参数）：

```ini
dram.refresh_enabled = true
dram.t_refi_ticks = 7800000
dram.t_rfc_ticks = 350000
dram.refresh_ticks_per_cycle = 333
dram.refresh_start_tick = 0
```

只有第一项是行为开关，其余是有来源的物理时间与时钟参数。start_tick=0表示
FastSim相对时间原点；没有将native CPI或结束时刻注入模型，也未认证与native
checkpoint恢复后的刷新相位完全相同。

实现位置：`include/fastsim/dram_refresh.hpp`、`src/simulator.cpp`；配置解析、校验与
JSON记录在config.hpp/config.cpp/main.cpp。实际行为为：

1. 每rank保存tick精度的下一准备事件、不可用截止、已发数据完成约束与观察计数。
2. 到准备事件后不再选择该rank的新请求，其他rank仍可参与选择；已预约命令完成。
3. 按bank已有PRE约束、关闭中bank的ready及在途数据约束，确定PRE/REF起点；
   已经关闭的空闲rank不无条件再加tRP。
4. REF期间阻止该rank服务，结束后所有行保持关闭。采用配置tRFC，不按请求加罚时。
5. 空闲的多个刷新窗口用整数运算跳过，无逐目标周期循环。状态随DramModel现有
   快照、channel安装和回退保留；测量reset仅重置观察计数，不重置物理相位。

当前gem5版本的准备事件递推已由短流日志核实：整数参数下前三次为7,785,681、
15,571,362、23,357,043ticks，即准备事件间隔tREFI−tRP，而不是自行假定固定
REF开始间隔。该策略来自本地参考版本，不是用负载拟合。

审查发现并修复一处重要边界：canonical/FCFS及写drain原先仅按arrival推进刷新，
同到达时刻的积压可以把命令预约到多个刷新周期以后，再在后续请求上触发overrun。
新增持续的每channel选择前沿；读积压及写drain反例先复现失败，修复后通过。

支持域：compact FCFS和具有causal selection边界的FR-FCFS；当前P1已满足。
mixed cross-Q/projected控制器显式拒绝该选项，不静默忽略。已有写方向日历、
row-cap重复PRE、隐藏bank准备和响应队列近似没有被本轮刷新实现宣称修复。

## 机制验证

- `fastsim_dram_refresh_tests`覆盖准备/完成边界、行关闭、另一rank先恢复、分数
  周期相位、长空闲跳转、状态复制、测量reset、参数拒绝、溢出、读积压与写drain。
- 初始边界测试在旧二进制上失败，新实现通过；canonical积压审查反例同样完成
  RED→GREEN。完整默认构建与fastsim_tests通过，相关Python检查9+7项通过。
  还在无预先tmp目录的隔离工作目录中复现并修复了测试夹具的目录依赖；最终
  standalone和完整测试均重新通过。
- 独立gem5刷新边界短流：精确tick响应完全一致；整数周期模式最大响应差约
  **0.526cycle**。无刷新边界的基础读流保持原结果；已知row-cap/read-full残差保留。
- 另补6条独立参考：读返回与刷新重叠、ACT/tRAS跨准备边界、预先关闭行、长空闲
  跨多周期、其他rank先恢复、恰好准备边界到达。生产probe按相同实际接收流重放，
  全部逐请求响应tick完全一致、参考零延迟准入，见edge-oracle-results.json。
- 两案关闭刷新后的全部既有目标字段均等于冻结P1。比较只排除明确列出的宿主
  时间/调度统计，以及新增配置字段和新增刷新观察对象，不忽略其他目标字段。
- 两案开启后的观测器重放也逐位中立。32个rank的相位/计数守恒检查通过。
  `totals.dram_refresh`统计的是推进到已观察控制器选择前沿的准备事件，**不是
  所有闲置rank直到整个程序结束的刷新总次数**。
- 每案609项参数检查及8,364个生产地址解码样本匹配；新增计时字段与捕获参数一致。

开启后重新导出最终流并送入G1，避免把CPU反馈导致的新到达流与旧流参考混用：

| 新开启流的arrival→data（cycles/读） | Marian | G500 |
|---|---:|---:|
| FastSim | 138.540718 | 127.255198 |
| 同流gem5 G1 | 136.438898 | 125.943928 |
| FS−G1 | +2.101821 | +1.311270 |

Marian参考有3次retry，实际准入相对提出时刻平均多0.004061cycle；G500为零。

因此均值±1cycle的预期尚未全部达到，不能宣称完整控制器等价；保留FR-FCFS/
row-cap等既有近似的影响。小型刷新边界一致不替代真实流对照。

## 吞吐测量

OFF/ON使用同一冻结最终二进制和同一配置，仅刷新开关不同；每案3对，交替
OFF→ON、ON→OFF顺序，同一CPU affinity96–111，所有自身验证/参考进程结束后
顺序运行。关闭逐请求导出。每次目标统计均与该arm的准确性重放比较，检查确定性。
共享主机的1分钟load采样范围2.67–9.60；本任务在吞吐期间没有并行编译、来源审计
或其他重放，不将其描述为独占整机测量。

测量吞吐分子为实际user UOP，分母不含功能warmup；另保留warmup、模拟器全程、
输入身份处理和整个CLI墙钟。不能把不同时间定义混成一个吞吐率。
