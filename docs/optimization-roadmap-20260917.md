# FastSim 瓶颈判断与后续优化路线（2026-09-17）

状态：**已有证据整理与后续建议，非实现完成报告、非新实验验收。**
本文记录本轮讨论的分析结论和优化手段。写入文档不表示已批准模型大改、启动矩阵、
切换默认或接受新的精度/吞吐权衡；下列候选均未因本轮讨论而实施。

最高层约束仍为 [项目目标与语义合同](project-goal-and-semantic-contract.md)，
所有评估遵循 [精度与吞吐报告合同](accuracy-reporting-contract.md)，尤其第 0、8 节。
默认保持 `configs/gem5-fs-native-kernel.cfg`：load-ready 配置与 bank/PRE store-wait
relief v2 开启，pending-fill 关闭；不调整 Q，不重开已否决的模型候选。

## 1. 核心判断：路线收益递减，不等于三个指标都已证明到顶

1. **CPI：当前局部修正路线的收益难以泛化。** 两阶段先计算每核基础时序，再处理
   共享访存及反馈。核心时间的修正不自动重建此前选择的 cache/coherence/DRAM
   路径；历史修正经常改善一侧误差，却恶化另一侧，或者增加过多宿主工作。
2. **PMU：不能从 CPI 瓶颈推出 PMU 也到顶。** 事件数相近不证明响应时刻和重叠执行
   正确；原生事件分类、访问次序和参数趋势仍需独立验证。nab 的旧 L2 异常已经确认为
   参考来源错误，不能继续作为新增 refill 或修改 coherence 的依据。
3. **吞吐：尚有不改变目标语义的实现机会。** 当前基础调度历史仍持续增长，逐 UOP
   时序返回对象混有大量统计，反馈也不能仅凭 `materialized` 计数少就认为已跳过
   大多数 UOP。存储、数据传递和重复计算是与精度修复不同的优化方向。

[9 月 16 日“精度天花板”综合判断](two-stage-accuracy-ceiling-20260916.md) 应用于
停止重复已经失败的路线，不能扩展成“所有两阶段实现都不存在更优方案”的严格下界
证明。本文收紧的是结论强度，不撤销其中的负实验、默认选择和重开条件，也不承诺
存在新的大幅精度收益。

**建议主线：工程上先做五组基础调度历史有界化，再独立评估统计热路径分离；研究上
优先找参数敏感度和配置排序的机制反例，而不是继续在同一批 40 案上压平均 CPI。**

或净成本条件，记录停止原因，不能捆绑 E2 掩盖回退。

## 4. E1：什么是“五组基础调度历史”

它们不是五个调度器，也不是流水线五个阶段，而是 `IntervalCoreModel` 第一阶段
lower-bound 调度所保存的五组历史时间。第二阶段仍独立处理共享服务与响应反馈。

| 数组 | 保存内容 | 当前主要消费者 | 有界化候选依据 |
|---|---|---|---|
| `completion_` | 每条 UOP 的完成时间 | 后继寄存器依赖就绪查询 | 已被 ROB 下界覆盖的旧 producer 不再提高 issue 下界 |
| `retirement_` | 每条 UOP 的退休时间 | ROB 容量、顺序退休、syscall 排空等 | ROB 相关近期历史及必要尾状态 |
| `dispatch_history_` | 每条 UOP 的派发时间 | fetch queue 约束、分支在途人口检查 | ROB 与 fetch queue 所需读集的并集 |
| `load_retirement_` | 按 load 序列保存的退休时间 | 基础 Load Queue 容量约束 | 队列容量对应的近期条目及独立绝对计数 |
| `store_retirement_` | 按 store 序列保存的退休时间 | 基础 Store Queue 容量约束 | 队列容量对应的近期条目及独立绝对计数 |

声明见 [interval_core.hpp](../include/fastsim/interval_core.hpp)，追加及查询见
[IntervalCoreModel::schedule](../src/interval_core.cpp)。截至本次核对，这五组仍使用
vector 持续追加；已经完成的 `ResidentCoreBuffer` ring 不是这一层，不能重复宣称
它解决了基础调度历史增长。

### 4.1 问题和可用证据

存储目前随处理记录数 N 增长，而模拟 ROB/LSQ 的容量固定。
[历史有界读集分析](global-optimization-screening-20260907.md) 中，LBM C32 仅
completion/retirement/dispatch 三组的有效元素存储估算约 7.2447 GiB；不包含
warmup、vector capacity、LSQ 或其他状态，不是当前总 RSS，也不是带宽饱和证明。

基础调度在相关 ROB gate 成立时有如下约束，i 为当前绝对 UOP 序号、R 为 ROB 容量：

```text
j <= i - R:
completion[j] <= retirement[j] <= retirement[i-R] <= dispatch[i] <= issue[i]
```

因此这类老 producer 的完成时间不再抬高本条指令的 issue 下界。但这只证明一类
时序读可以简化，不自动证明分支、审计或所有配置都能删除旧条目。

### 4.2 建议实现边界

1. 先枚举全部读写点、reset 点、调用方和诊断消费者，再选择 ring/滑动窗口表示。
   不把“只保留最近 192 条”当作通用规则，容量来自当前目标配置及实际读集。
2. 历史分析给出的候选容量是：completion/retirement 各 R+1，dispatch 为
   max(R, fetch_queue_entries)+1，load/store history 各为对应队列容量+1。
   这是待完整验证的方案，不是已经通过全路径证明的实现规范。
3. 将绝对 UOP/load/store 序号、总退休数和 audit 边界与容器长度分离。
   当前 `completion_.size()` 等兼任绝对计数，替换容器时不能改变这些语义。
4. 保留老依赖存在性、类别和统计；不能把 producer distance 改成 0，不能让已回收
   序号读到绕回后的新条目。若某路径确实需要旧精确值而尚无等价表示，保留原路径。
5. 只处理这五组历史。cycle-indexed issue/writeback/IQ/port 状态和
   `dependency_audit_producer_seen_` 有不同生命周期，不一并删除或换环；不宣称
   整个模拟器内存因此变为 O(ROB)。

### 4.3 首个实验与停止条件

- 建立完整历史实现作为对照，逐 UOP 比较时序输出、资源状态和计数，再比较完整
  warmup+ROI 的目标结果。覆盖远距离/扩展依赖、分支预测错误及 audit、syscall、
  fence/atomic、预热 reset、跨 chunk、ring 多次绕回和容量边界。
- 分别测五组有效字节、allocated capacity、整进程峰值 RSS 随 trace 长度的变化；
  不拿容器字节替代 RSS，也不拿组件循环速度替代生产吞吐。
- 完整目标状态必须 bit-identical。若新取模、边界检查或 fallback 抵消速度收益，
  如实标为“仅内存收益”或停止；有稳定吞吐回退时不能自动合入默认。
- 首轮没有目标状态等价证明，或需要近似删除依赖才能通过，立即停止该实现方向。

## 5. E2：分离统计传递和时序热数据

当前 `IntervalTiming` 带有时序和大量统计字段；producer 接收后再逐项累计到 chunk。
[9 月 7 日采样](global-optimization-screening-20260907.md) 中，核对过的统计累计
指令块占四份 profile 的 sampled CPU cycles 约 3.43%–5.18%。这是旧二进制的局部
指令采样权重，不是可直接删除的 wall time，也不支持预报两位数百分比提速。

建议先检查当前编译产物和热点，再将操作必需的时序 payload 与累计 PMU/audit
分开；在事件所属状态累计，在安全的 chunk 边界交付。静态元数据只在证明输入
不可变且 cache key 完整后复用，不缓存跨目标配置的调度结果。

必须分别保持 sum、max、作用域、预热 reset、部分接受/退休前缀和重试语义；producer
提前生成的未接受后缀不能提前计入测量。不能通过关闭统计、少报 PMU 或把 max 改成
累计差分来提速。与 E1 使用相同的目标状态完全等价和独立吞吐门禁。

## 6. R1 与 D1：用参数趋势和事件证据选择精度修复

### 6.1 从一个参数族的可重复反例开始

首批可在已有支持的 ROB 或 cache 参数中选一个族，明确 baseline 及两侧取值，
保留有效激励和反向控制。先审核可复用数据是否满足新合同；历史目录名和采集计划
不能代替共同窗口证明，也不能未经批准直接重采 204 案。

完整报告同时包括绝对 CPI/PMU、相对 baseline 的变化方向与幅度、跨配置排序，
不能用排序改善掩盖绝对误差。微小参考变化的 tie/material 阈值必须事先冻结，
单独报告 raw 与 material 结果；独立负载或窗口不能参与候选选择。

归因顺序为：确认参数实际激活 → 找到受影响的请求/资源状态 → 核对关键消费者与
退休跨度 → 形成通用机制假设 → 小范围控制实验 → 完整回归和独立泛化门禁。
离线 gem5 标签只用于核对，不进入推理；跨配置结果复用也必须证明功能输入与
状态依赖成立，不能假定改变微架构后多线程执行流一定不变。

### 6.2 CPI 保留首个分歧追踪，不继续扩大补偿

[v2 后续控制实验](store-wait-v3-critical-bank-20260916.md) 已证明 Graph500 C32
的回退可由 warmup-only 干预复现，measurement-only 则恢复 off 的相应结果。
这足以把下一步收紧到预热首个请求分叉、TSO send 和共享到达的传播状态；尚未证明
每个保留状态的独立贡献，不能把服务周期总和当作 CPI 误差的加性分解。

继续调查须保留 LBM 及 TeaLeaf/NAMD 等相反误差方向的控制，不能按 workload、PC
或误差符号选择性扣周期。组件语义证据和整机 CPI 验收分开；一个指标变好不等于
全局正确，候选暂不推广也不等于否认已证明的组件问题。

### 6.3 PMU 优先调查有实质事件影响的分类分歧

先验证原生来源、scope、人口和守恒，再检查按层级/请求身份的事件分类差异，结合
绝对计数误差、相对误差和参数变化选择调查对象。hits、tag misses、upgrades、
merged misses、remote supplies 不得折算以制造命中。需要逐请求证据而只有汇总时，
先声明缺口并申请最小诊断，不能从汇总数臆造请求因果链。

nab 旧 path-class 来源的问题已闭合，不实施 `shared_line_l2_refill`。修复参考来源
不是模型收益；PMU 计数接近也不能单独证明响应时序或 CPI 正确。

## 7. R2：较长期的精确块级状态转移

真正减少宿主工作量的研究问题是：能否把一段 UOP 的状态更新组合成精确转移，
从而减少第二阶段逐 UOP 扫描，而非仅减少“发生位移的 UOP”计数？

[历史活跃路径审计](architecture-evidence-audit-20260907.md) 中，fast-kernel
实际处理数等于 accepted UOP 数，`materialized_uops` 仅统计发生位移的部分。
新原型必须报告实际循环次数、证书成本、覆盖率和 fallback 成本，不能重复混用。

边界要求：依赖传播、IQ/LSQ/ROB、dispatch/retire、统计和 reset 均有等价证明，
不能只证明块末尾周期相同。无法证明安全的路径必须在修改状态前回到现有逐 UOP
实现，或具有完整可恢复状态；证明本身的代价也必须计入端到端吞吐。

这是待批准的研究方向，不是本轮实现计划，不默认增加第二遍完整 closure，也不
重开全核心跨 Q continuation。可参考
[ZSim 原论文](https://people.csail.mit.edu/sanchez/papers/2013.zsim.isca.pdf)
中减少动态重复工作、复用静态处理的思路；不直接外推其速度或精度到 FastSim。

## 8. 共用验收、报告和停止条件

### 8.1 E1/E2：无损工程优化

1. 冻结旧/新二进制、完整配置链和相同 functional 输入；机制改动与宿主优化分开。
2. 通过默认构建、`./build/fastsim_tests`、定向等价测试及相应 sanitizer 检查。
   `ctest` 无注册测试，不能替代直接执行测试二进制。
3. 比较 `scope_metrics`、逐核/线程、cache/CHA/DRAM、资源生命周期和守恒计数；
   只排除事先列明的 wall/throughput、host-only timer，以及已有合同认可的宿主
   调度计数。不能因为 aggregate CPI 一样就忽略目标中间状态或 PMU 差异。
4. 先小范围语义对照，再完整冻结回归。五组存储有界不等于模型精度提升。
5. 固定 quiet host、CPU/NUMA、worker 数和 page-cache 条件，单 case 串行至少五轮
   交错 A/B；报告中位数、范围、measurement user-UOP/s、包含预热的端到端耗时、
   峰值 RSS。并行矩阵的 cases/hour 单列，不能代替单例吞吐。
6. 执行既有吞吐准入门槛，不在看到结果后放宽。样本受争用或缺基线时标为未验收；
   没有净提速则不宣称提速，只有内存收益但存在速度代价时需另作产品取舍。

### 8.2 精度或新表示候选

- 单独运行 `tools/validate_fs_oracle_identity.py`；通过维护原生验证器进行来源、
  scope、人口和守恒检查。已有预测重评使用 `--source-root` 与 `--stats-dir`。
  `passed` 不等于身份、精度阈值、吞吐或硬件 strict PMU 认证。
- CPI 逐案同时报告相对误差和绝对误差，聚合含 CPI MAE；PMU 同时报 finite cases、
  MAPE、P50/P90/P99、WAPE 和 signed bias。缺原生 cache 证据时 fail closed。
- 新精度机制必须同时检查正负尾部、参数趋势、独立负载/窗口和吞吐；不能仅凭
  局部等待下降、修正次数非零或一个窗口改善进入默认。
- 没有首个机制见证、可影响范围或成本证据，就停在诊断；小范围控制失败就不扩
  长矩阵寻找偶然改善。无法跨负载泛化的残差补偿不能成为维护参数。

### 8.3 明确不采用

- 增大 Q、缩放目标 latency、删除 cache/LRU/TSO 更新或少报 PMU 来换吞吐。
- 按 memory-penalty 标签直接扣退休残差，或扩大 credit 掩盖另一个状态错误。
- 未满足重开条件就恢复 projected-DRAM、pending-fill 或完整跨 Q 重构路线。
- 将 40 案既有回归集当成新的独立泛化证明，将代理参考纠正当成模型优化。
- 在本轮文档任务中修改模拟器、启动新实验、切换默认、提交或推送。
