## 1. 绝对误差不是小分母现象

这里的 CPI 是 active cycles / macroinstructions；所有四个 LBM case 的
gem5/FastSim 宏指令分母完全相同。绝对误差单位为 cycles/macroinstruction。

| 核数 | gem5 CPI | FastSim CPI | 相对误差 | CPI 绝对误差 | 总 active 周期差 |
|---:|---:|---:|---:|---:|---:|
| 4 | 3.660593 | 3.427716 | −6.3617% | **0.232877** | −7,397,687 |
| 8 | 3.514107 | 3.421476 | −2.6360% | 0.092631 | −5,825,092 |
| 16 | 3.748229 | 3.729862 | −0.4900% | 0.018367 | −2,299,588 |
| 32 | 4.033514 | 4.246714 | +5.2857% | **0.213200** | +53,291,997 |

LBM 的基准 CPI 在 3.5–4.0 左右，6% 左右的相对偏差就对应约 0.2 CPI。
这不是把 0.01 和 0.02 比较后得到很大的百分比。

Cache miss 数量也不是主要矛盾：C4 的 L1D/private-L2/LLC tag misses
相对误差分别为 +0.0502% / +0.1033% / +0.0607%；C32 分别为
+0.0868% / +0.0237% / +0.0287%。但 miss 计数相近不能证明请求的准入、
响应、合并或 SQ 释放时间相近。

## 2. 全量配对方法与可信边界

沿用 [TeaLeaf 完整 ROI 审计](tealeaf-full-roi-error-audit-20260910.md) 的流程：
先固定输入、ROI、线程、CPL、分母，再配对全部 hardware records 的
fetch/issue/retire，最后对选定窗口关联 native admission/response 和阻塞者。

- gem5 使用原采集二进制，仅开启 JSON 功能记录、阶段标签与 native v7 响应旁路。
  C4 四核的功能边界、CPI、kernel events、native summary 均与冻结参考相同。
- 隔离的 FastSim 阶段导出器只写出被接受的 UOP 时序。C4、C32 导出运行的
  `scope_metrics`（吞吐除外）与逐线程周期均和生产运行完全一致。
- C4 全量核对 **40,660,521 条硬件记录**，另有 **30 条 syscall 辅助记录**
  没有 gem5 O3 stage，明确排除。实际执行的内核硬件指令全部保留。
- 每条记录核对 core/thread、序号、PC、物理地址、大小、op/CPL、操作数数量、
  load/store/atomic/branch/microop 标志。FastSim 输入仍为原完整依赖 FST。
  JSON exporter 只输出四个 inline producer，因此这里不把 JSON 配对说成
  已逐条核对全部扩展 RAW 依赖。
- gem5 的 load `complete_tick` 是地址生成完成，不能作为数据响应。数据返回
  使用 native v7 `native_last_response_tick`。

C4 与 C32 的完整 FastSim 阶段已导出。C32 gem5 于 2026-09-11 按用户要求
发送 SIGINT，正常退出模拟循环并完成文件刷新；全量等待任务同时终止。
原采集器保留退出码 2 / `collection-failed`，不改写成完整采集成功。

保留的测量记录为 **321,720,189 / 324,124,074（99.2583%）**：

- core1–31 均完成原计分区间，功能边界、CPL、CPI、kernel events 与冻结参考
  完全一致。native summary 的语义计数也一致；仅全局退出后的
  `target_drain_polls` 从 9 变为 0，以及 JSON 输出启用标志不同。
  该轮询字段来自 `pollFunctionalTargetDrain()`，不是工作核的访存或阻塞统计。
- core0 有 **8,053,175 条测量记录**，其中 **7,645,557 条用户 UOP**，另含
  内核记录及 30 条辅助记录；缺少原终点前的 **2,403,885 条记录**。
  core0 的阶段比较只到同一条已采记录，不能拿此范围替代原完整 CPI。
- 停止时 core0 有 **32 条未结束的 native 生命周期**，全部为普通 store，
  其中 1 条已准入、31 条尚未准入；单独保留其动态指令 ID 及状态。
  它们的已退休阶段可分析，未观察到的访存响应不补为零延迟。
- records/labels 的文件尾均完整写出并以换行结束。对已采范围进行逐记录身份
  核对与互斥阶段记账，不重新运行 FastSim，不重新采集 gem5。

该范围覆盖 31 个工作核的完整正误差增长及 core0 跨 worker EOF 的反向增长，
后续结论明确区分已采范围与原完整 C32 参考。最终逐条核对
**321,720,159 条 hardware records**，排除 30 条辅助记录；32 个已采区间的
阶段周期及各 PC 分类周期均严格守恒。

## 4. 已发现的输入边界机制问题：计分结束不等于停止干扰

采集器 `TaoTrace::noteFunctionalRecordEmitted()` 在每核达到目标时：

1. 冻结该核 FST、CPL 与 PMU；
2. 关闭该核的 native/frontend 观测；
3. **继续运行该 CPU**，直到所有核达到目标，再执行全局 drain/退出。

FastSim 的 `WarmupInstructionTraceSource::next()` 则在该核的
`take_records` 用完后返回 EOF，随后不再产生该核后续真实访存。
因此，两端用于计分的各核指令相同，但较慢核的竞争环境不完全相同。

gem5 最终 committed UOP 计数减去已采集记录数显示，C4 有约 **46,162,053**
条额外 UOP，主要来自三个较快核；C32 约 **557,120,213** 条。
这些计数还包含很小的目标边界/drain 差额，不是精确的后缀访存计数。
gem5 全局 `stats.txt` 的 DRAM/ROB 统计覆盖这些后续执行，不能直接减去
FastSim 计分区间内的同名统计。

C4 core0 在其他三核最后一个计分终点对应的同一指令处：

| core0 的位置 | gem5 已过周期 | FastSim 已过周期 | 累计差 |
|---|---:|---:|---:|
| ordinal 3,260,493；约测量流 31.5% | 21,538,682 | 21,364,648 | −174,034 |
| 原测量流结束 | 53,150,289 | 47,934,963 | −5,215,326 |

此后累积 **5,041,292** 周期欠估，占 core0 最终欠估约 96.66%。
这是时间分界证据；下面的隔离实验进一步检验了实际影响，而不是把该相关比例
直接当成修复收益。

### 真实后缀的隔离结果

使用同一 gem5 二进制和 checkpoint，仅把采集上限移到原运行的共同结束时刻
`22091747555916` tick，得到较快三核的 **46,072,637 条真实后续功能记录**。
原范围的 FST 热记录和完整 `.deps` 前缀逐字节相同；`.asmap/.vmap` 前缀一致。
新采集的静态 `.imap` 会新增记录并使少数原映射失效，因此将原静态映射冻结，
只适配其 source-record-count 头字段；原映射本来就没有 complete-map 标志，
未知后缀 PC 使用既有 fallback。

必须通过的两个控制已通过：

1. 使用这些新输入、仍截到原测量终点，逐线程周期和所有计分指标与原结果完全一致。
2. 扩展后缀输入上，生产二进制与阶段导出二进制的目标结果完全一致。

计分仍是原来的每核 10M user UOP，宏指令总分母仍为 31,766,542。
core0 的原指令流不扩展，只有三个较快核继续执行真实后缀。

| C4 输入 | gem5 CPI | FastSim CPI | 相对误差 | CPI 绝对误差 | active 周期差 |
|---|---:|---:|---:|---:|---:|
| 原逐核截断 | 3.660593 | 3.427716 | −6.3617% | 0.232877 | −7,397,687 |
| 补回真实后缀，计分范围不变 | 3.660593 | 3.623955 | **−1.0009%** | **0.036639** | **−1,163,881** |

模型、时序参数和计分分母均未改变，净周期缺口减少 **6,233,806 cycles / 84.27%**。
这构成了边界问题的干预证据，而不是按目标 CPI 添加补偿。

core0 的普通 store 数保持 1,647,991，L1D miss 数完全不变，L2 miss 仅增加 5。
其串行 store 服务累计从 47,857,736 增到 54,033,420，增加 **6,175,684 cycles**，
对应 core0 新增的 6,226,291 cycles 的 **99.19%**。结合普通 store 生命周期
不重叠及 SQ 释放者配对，变化明确落在 store 排空服务链，不能解释成多执行了
计分指令或靠增加 miss 数拟合 CPI。

不过，core0 从 −5,215,326 变为 **+1,010,965** cycles，其他三核仍分别为
−735,005 / −1,243,068 / −196,773。逐核绝对周期误差之和从 7,397,687
降到 3,185,811，减少 **56.94%**；按宏指令加权后的逐核 CPI 绝对误差仍为
**0.100288**，高于相互抵消后的整体 0.036639。

该实验不是完整修复验收：三个后缀在 FastSim 中结束于 53.82M / 52.09M /
51.66M cycles，早于 core0 的 54.16M cycles，尾部竞争仍不完全覆盖；core0
也已暴露正向模型误差。固定静态映射用于隔离变量，尚未解决采集时长改变
`.imap` 的一般问题。原始共同时间截断按配置逻辑返回预期的退出码 2，不能
把它当成新的完整参考 oracle；其最终 tick、功能前缀和推理控制均另行验证。

## 5. SQ 释放链与局部访存见证

下文的“DRAM store”指原始 store 的 native 路径为 `ruby_memory_read`：
store miss 等待取回缓存行/取得权限。它不是“每条架构 store 同步写 DRAM”。
LLC 脏驱逐引发的控制器 writeback 是另一类事件，不能与这些 store 的
line-acquisition read 混计。

本轮不仅观察了局部 SQ 样本，还关联了 C4 全部 **4,829,060 条普通 store**
的 native commit/resolution。86 条没有 Ruby 请求；其余 **4,828,974 条**
均有终结响应，包含 core1 的 8 条多次准入 store。各核普通 store 的
`first admission → last response` 区间按程序序完全不重叠。

这一点还与目标源码吻合：实际配置 `needsTSO=true`，gem5
`LSQUnit::writebackStores()` 在 `storeInFlight` 为 true 时不发送下一条普通
store，发送后置 true、完成时清零。这是当前 gem5 O3 配置的具体实现行为，
不应泛化成“TSO 架构必然只能有一条访存请求在途”。

| 核心 | gem5 普通 store 在途周期，裁剪到 ROI | 占该核 elapsed 时间 |
|---:|---:|---:|
| 0 | 51,127,897 | **96.19%** |
| 1 | 20,031,227 | 93.00% |
| 2 | 19,320,353 | 94.25% |
| 3 | 19,816,860 | 93.88% |

每核严格满足“store 在途区间 + 相邻 store 的空隙 + 首尾边界 = elapsed ROI”。
这里是已验证不重叠的区间覆盖率，不是将所有 load/store 等待盲目相加。
它支持以下传播链：**store 响应偏早 → TSO 排空偏早 → SQ 槽位偏早释放 →
后续栈 store 和指令更早进入流水线 → CPI 欠估**。core0 的额外访存竞争丢失
正是通过这条高占用路径放大的。

实际运行磁盘镜像内的 LBM ELF 已与工作负载构建产物逐字节核对，SHA256 为
`5e101a0f92be48ed2b1fde4608d1b39ab7ad9823a7ede8bb3fb95107b34d008e`。
热点位于 `LBM_performStreamCollideTRT._omp_fn.0`。

- `0x406655`、`0x406669`、`0x40667d`、`0x4066b9` 等是保存邻居地址的栈 store。
- `0x4064d8` 读取网格标志；`0x406710/0x406724` 是正常网格路径的 load。
- `0x406990` 开始 obstacle/bounce-back 路径。C4 core0 的该条件分支
  taken 为 26,871 / 31,839；worker1 为 520 / 12,536。C32 分别为
  33,832 / 36,185 与 410 / 12,694。线程的路径组成确实不同。

对完整流分析后选出的 ordinal 2,000,000–2,010,000 和
5,000,000–5,010,000 窗口，FastSim 发射前 ROB 头等待几乎全部由
**SQ 容量释放门**直接决定。不是简单的取指等待或遗漏寄存器依赖。
追踪的是当前头部 store 的 `incoming_sq_release_sequence`，再关联 gem5
同一较早 store 的 native response。

| 已对齐的头部 store 样本 | 样本数 | gem5 issue − SQ 释放者响应，均值 | FastSim issue − 释放，均值 |
|---|---:|---:|---:|
| C4 core0，2M 窗口 | 391 | 2.83 cycles | 3 cycles |
| C4 core0，5M 窗口 | 404 | 3.09 cycles | 3 cycles |
| C32 core1，2M 窗口；该核完整区间 gate 已通过 | 113 | 2.99 cycles | 3 cycles |
| C32 core1，8M 窗口；该核完整区间 gate 已通过 | 97 | 2.58 cycles | 3 cycles |

这些样本说明，SQ 释放到后继 store 发射的关系已有对应机制。后续优先检查
**释放者收到响应的时间、TSO store 准入顺序及其内存竞争环境**，不能因为看到
大量 SQ 阻塞就直接增加 SQ 容量或固定等待。

同一行 follower 的过早数据可用性也仍然存在。例如 C4 core0：

| 记录 | 作用 | FastSim issue | FastSim 数据响应 |
|---|---|---:|---:|
| 2,000,072，PC `0x4069fd` | cache line 5,734,961 的 DRAM parent load | 13,403,018 | 13,403,217 |
| 2,000,076，PC `0x406a0e` | 同行 follower load | 13,403,020 | **13,403,022** |

gem5 将 follower 合并到未完成请求，native 准入到响应为 **184 cycles**；
FastSim 给出 2 cycles。可是该 follower 在 FastSim 的 retire 为 13,403,218，
仍晚于 parent 响应。本轮 C4 core0 2M 窗口找到的 324 个此类见证，直接退休
都已被较早指令挡住。因此不能用 `324 × 等待差` 解释 CPI，也不能由此直接
重新启用以前未通过泛化验证的 pending-fill/line-coalescing 组合。

此外，FastSim 当前 canonical cache/DRAM 处理与 response-side store drain
仍分离。`store_latency_cycles` 来自较早共享调度结果，随后用于
`store_send + store_latency_cycles` 的 SQ 释放；生产配置下相关 store
post-commit/shared-service 候选仍关闭。未来修复需要保持服务所有权、真实
准入次序和可见性一致，不能把两条时基的差直接补成额外延迟。

## 6. C32 后段 store 服务高估与混合读写退化路径

C32 并非每个核都高估：core0 少算 **11,050,652** cycles，其他 31 核合计
多算 **64,342,649**，相抵后为 +53,291,997。C16 的小净误差也有抵消：
core0 多算 2,424,602，其他 15 核合计少算 4,724,190。

### 31 个工作核完整区间的周期账本

停止采集后，31 个工作核仍具备完整原计分区间。它们全部出现正向的
`fetched_not_issued` 差额，合计如下：

| 31 核互斥周期类别 | gem5 | FastSim | FastSim − gem5 |
|---|---:|---:|---:|
| 尚未 fetch | 789,391 | 77,283 | −712,108 |
| 已 fetch、尚未 issue | **603,708,322** | **660,310,973** | **+56,602,651** |
| 已 issue 的 load 尚未 retire | **233,904,945** | **263,236,927** | **+29,331,982** |
| 已 issue 的 store 尚未 retire | 11,607,027 | 3,423,466 | −8,183,561 |
| 已 issue 的其他指令尚未 retire | 766,533 | 26,502 | −740,031 |
| 有退休的周期 | 73,526,711 | 61,567,066 | −11,959,645 |

表内差额合计 64,339,288，加首边界差 2,059 和 idle 调整 1,302，严格得到
**64,342,649 cycles**。发射前等待与已发射 load 等待均有正差额，同时存在
其他阶段的负差额；不能用单一 PMU 或把所有“stall”计数相加解释净误差。

进一步完整关联典型 worker1 与两个误差最大的 worker4/13 的普通 store，
共 **3,174,918 条**，全部有终结结果。每核 Ruby store 生命周期完全不重叠，
严格满足“在途 + store 间空隙 + 首尾边界 = elapsed ROI”：

每核有 10 条无需 Ruby 的 store，其余全部为单次准入；本表不把未扫描的

native DRAM store 服务从初段约 251–254 cycles 升至后段约 287–298 cycles。

C32 core1 的完整阶段比较确认：前约 250 万条记录总体略欠估，约 300 万条
附近转为高估；50% 处约 +29.7 万周期，80% 处约 +127.3 万，最终
**+200.3 万周期**。这与原来的前缀观察一致，并补齐了该工作核完整后段。

在同一 core1 的两处 10,001-record 窗口内，按实际动态指令关联 native 响应：

| 同一指令类别 | 2M 窗口样本数 | gem5 / FastSim 平均服务 cycles | 8M 窗口样本数 | gem5 / FastSim 平均服务 cycles |

| DRAM store | 105 | 271.04 / 267.20 | 92 | **294.66 / 420.46** |
| DRAM load | 32 | 286.38 / 265.59 | 32 | **271.69 / 414.03** |

前段窗口 gem5/FastSim 耗时为 29,741 / 28,955 cycles，后段为
31,452 / 44,460 cycles，后段多算 **13,008 cycles**。被选普通 store 的 native
生命周期逐一确认不重叠，其 native/FS 服务和为 28,430 / 40,926，差
**12,496 cycles**。这些服务区间没有裁剪到对应的 retirement 窗口，不能把
12,496 / 13,008 当成精确贡献率，但与 SQ 释放者配对共同说明差异落在串行
store 的响应服务上，而不是后继 store 接到释放后又多等了约百周期。

这个后段窗口结束时，距离 gem5 第一个核心的计分终点仍有 **6,179,602 cycles**，
FastSim 侧也还有 **6,585,674 cycles**。因此窗口内两端所有核心均仍在执行
已采集范围，尚未出现逐核 EOF；这段正偏差不能归入 C4 已证明的后缀缺失。
它是需要独立处理的时序模型差异。

同批 DRAM 请求的 canonical command − arrival 均值由 105.68 增至
257.61 cycles；后段 124 个请求中，85 个由 channel 日历阻塞、14 个由 bank
日历阻塞，其中 12 个的直接阻塞者是无架构指令 ID 的写回请求。这是当前模型
中的等待来源，尚不等于 gem5 中同一命令级阻塞者的逐一配对。

进一步的只读阶段观测暴露了更具体的退化条件：
`apply_frfcfs_dram_repair()` 将整个 materialized 批次的 `descriptor.replayable`
相与；任何脏行驱逐触发 DRAM 写回后，该批次都不能进入时序重排，保留 canonical
FCFS。当前 C32 34,018 次候选中只有 **3,275 次 stable**，有 **30,743 次 fallback**。
只读原因计数进一步确认：本次 **30,743 次 fallback 全部因脏写回使描述符
不可重放**，占候选 **90.37%**；其余 3,275 次全部 stable。没有合并请求、
原子访问或后续收敛检查导致的额外 fallback。计数与生产总量严格守恒，
诊断运行逐线程周期和全部计分目标与生产结果完全一致。

全量 accepted-prefix 观测与生产结果完全一致。core1 约 100 万记录时全局仅
有 7 次 DRAM 写回，300 万时约 20.9 万次，800 万时约 217.7 万次。从约
200 万记录起，相邻 core1 accepted prefixes 之间持续出现脏写回。
直接的候选调用记录也确认：包含 core1 2M 之后访存的全部候选批次均因
脏写回而退回，8M 所在百万记录段的 396 次候选无一执行 FRFCFS 重排。
因此已证明该退化路径实际覆盖高估增长的后段；尚未独立测定它对完整 C32
周期高估的贡献，不能将两者画等号。

源码还显示，当前 `open_adaptive` 的排队冲突预充电只在
`DramModel::schedule_frfcfs()` 中处理。fallback 的普通 read 路径和
`drain_write_burst()` 都调用 `access_decoded()`，仅处理 row-access cap，
没有扫描相应已准入队列的 adaptive page policy。gem5 则在真正的读/写
burst 服务时检查当前队列。因而这里既有选择顺序退化，也有 page-policy
执行路径差异；具体各贡献多少周期仍需独立干预，不能依据源码差异直接填数。

写队列调度也缺少真实的 read-queue-empty 事件：gem5 在无待读且写队列超过
低水位时主动服务写回；FastSim 只在下次 read 或写队列满时推进排空。
这会改变闲时写回、强制排空与后来 read 的相互竞争，属于应纳入同一混合读写
事件调度的机制缺口，不应通过调整 LBM 的固定写回延迟补偿。

## 7. 下一步机制修复的边界

后续源码与接口设计见 [两阶段机制修复设计](lbm-two-stage-mechanism-repair-design-20260911.md)，
覆盖计分/执行边界、混合 RD/WB、跨 Q 服务身份、实际 store 准入和局部核心恢复。

优先分离“计分结束”和“执行结束”，而不是向 LBM 加固定 DRAM 延迟。

- 采集端：冻结每核计分 oracle 后，仍需保留为其他计分核心产生干扰的真实
  功能流、完整 RAW、地址空间及 CPL/idle 识别状态；不能仅删除一个 EOF 判断，
  却让辅助状态停在旧终点。
- 推理端：`take_records` 的计分终点需要独立于 context-tail 的执行终点。
  原核心、cache、coherence、DRAM 和 response frontier 继续推进，只冻结
  对应记录的计分累计。仍使用当前两阶段推理，不读入 gem5 时序标签。
- 性能边界：这次后缀增加约 2.95 GB 的 64-byte 热记录，不含扩展依赖和映射；
  需处理的功能记录由约 40.66M 增至 86.73M。计分 marker 本身成本很低，但
  额外真实工作量不免费，不能把端到端吞吐成本说成零。优先使用应用阶段对齐、
  干扰窗口覆盖可验证的采集方案，避免用大量无关长尾维持背景执行。
- 验收需同时检查原计分人口、context-tail 覆盖、逐核绝对误差和共享请求时序；
  接受边界正确化可能揭露原来被欠估抵消的正误差，不以净 CPI 恰好靠近零为准。

混合读写路径的具体修复入口是现有共享阶段，而不是另建逐 UOP 的因果模拟器：

1. 共享 cache weave 在产生脏驱逐时，同时记录写回事件的地址、触发者、次序与
   到达约束；不能只有 demand read 描述符，却让写回悄悄改变 DRAM 状态。
2. 当前批次的 DRAM 求解同时接收 demand read 和脏写回事件，沿用跨批队列、
   bank/row/方向状态，处理已准入队列的选择、读空闲时的排写及 adaptive PRE。
   用这次求解替代当前退回路径的工作，不追加第二遍完整指令推理。
3. 将返回值关联到原事件及真正的 store drain 服务者；保持 admission、response、
   SQ release 的所有权与守恒。只把 `replayable` 强制设为 true 会丢失写回副作用，
   不能作为修复。

这些是机制接口要求，不是已验证实现，也没有当前实验未测出的吞吐收益保证。
31 核完整阶段与 core0 已采账本、代表工作核的完整 store 生命周期已足以
确定下一步范围。混合读写路径各项机制的独立修复收益仍未测定，不能把
全部 +64.34M worker 周期误差直接归给 FRFCFS fallback。
目前没有证据支持统一增加等待、改变 SQ/ROB 容量、扫描 FRFCFS 窗口，或直接
启用以前失败的 pending-fill/shared-service 组合。

## 8. 本轮耗时与吞吐口径

本轮耗时数小时的是 gem5 O3 的详细参考采集及逐指令 JSON/native 观测，
不是 FastSim 推理。C32 采集按用户要求停止，进程总耗时 **12,728.4 秒**；
没有补采。C32 的 FastSim 生产结果记录了 320,000,005 条用户 UOP，
测量吞吐为 **3.922648 MUOP/s**，对应测量计时约 **81.58 秒**。
只读 FRFCFS 原因导出运行的整个进程耗时 **88.36 秒**，计分指标及逐线程
周期均与生产结果完全相同。两个计时边界不同，不能直接把差额认作插桩开销。

历史口头表述“平均 5 MIPS”若来自 `user_uops_per_second`，准确单位应为
**百万用户 UOP/秒（MUOP/s）**。LBM C32 同一区间有 247,917,967 条用户
宏指令，因此其生产计时折合 **3.039046 百万用户宏指令/秒**。跨负载平均值
也不保证每个 case 都达到该速度。

gem5 在较快核到达计分终点后继续执行这些核，且保留详细 O3/Ruby 时序。
其实际执行量大于冻结的计分输入；JSON 已输出记录数不能当作 gem5 全部
执行指令数。参考采集、FastSim 推理和离线配对必须分开汇报。本次中途核对
记录在 `throughput-scope-snapshot.json`；其中 gem5 耗时和进度是带时间戳的
快照，不是完成耗时。后续模型验证复用已通过对应范围核对的参考；本轮停止
后的 core0 数据不冒充完整参考，不因每次 FastSim 改动重采。
