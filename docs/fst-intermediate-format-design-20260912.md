# FST 统一中间格式与微架构探索设计

日期：2026-09-12。

状态：**方案记录，尚未实施。** 本文整理当前讨论结论，不修改现行 FST
字节规约、采集策略、FastSim 执行逻辑或精度验收规则，不授权重采数据。
事件名称和字段是语义建议，尚未分配磁盘枚举值、位号或固定大小。

## 1. 目标与时序原则

FST 应作为 gem5 functional trace 和 DynamoRIO drmemtrace 共用的中间格式：

> 固定功能工作量，保留执行所必需的初始条件和因果约束，由目标微架构重新计算时序。

同一份 trace 在不同 ROB 容量、执行宽度、缓存和内存配置下，指令退休时间、
跨核访存交错、资源竞争和各核完成顺序发生变化，是预期的预测结果。

“各核处于同一时间轴”指同一次 FastSim 推理中，各核按目标模型预测的模拟时间
竞争共享资源；不要求复现采集时的时间戳，也不要求各核同时完成。

因此，不能仅因某核先耗尽 FST 就判定采集错误、补齐该核的工作量、增加固定等待，
或把完成时间强行拉齐到 gem5。需要修复的证据应是功能工作缺失、必要依赖丢失、
身份混淆或边界语义不一致。

项目继续采用当前两阶段推理框架。本文不提出引入 `causal_read`、完整 OS 调度器、
新设备或按负载补偿。

## 2. 当前基础与缺口

| 项目 | 当前情况 | 本方案处理 |
|---|---|---|
| 功能指令主流 | v7 的 72 字节头、64 字节主记录 | 保留紧凑主路径 |
| 寄存器 RAW 依赖 | 主记录四槽与 `.fst.deps` 扩展共同表达 | 保留，不能把四槽误认为四条依赖上限 |
| syscall 元数据 | 每个 syscall 对应稀疏 128 字节行，包含字段有效位 | 保留既有语义 |
| 地址空间与映射 | 已有地址空间、虚拟页和取指映射等附件 | 继续按能力声明使用 |
| gem5 软件线程身份 | syscall 元数据未声称提供 guest OS TID | 需要独立身份模型 |
| 普通跨线程阻塞与唤醒 | 当前未形成完整可消费的统一合同 | 按需增加稀疏事件 |
| 原始 DR 指令转换 | syscall 映射已有规约，完整指令路径仍需解码、UOP 转换和依赖构建 | 不能把元数据兼容称为完整转换已完成 |
| 输入结束处理 | 完成流不再提供新工作，其他流继续处理 | 保留固定工作量完成语义 |

依据：[现有 FST 转换规约](fst-v7-drmemtrace-conversion-contract.md)、
[完整依赖设计](fst-complete-dependencies-20260909.md)、
[类型定义](../include/fastsim/types.hpp)、[读取实现](../src/trace.cpp)。

当前 `src/simulator.cpp` 的 `worker_loop()` 在生产者读完输入后停止生产；
`compact_epoch_buffer()` 在消费者处理完末尾批次后设置 `finished_`。
主循环等待所有流完成。提前结束不会自动清空该核缓存，也不会为了等待其他核
而把该核 CPI 周期延长到最晚完成时间。

这些实现表示“固定输入耗尽”，不证明真实软件线程退出，也不证明所有内存事务
在该瞬间已经物理完成。退休、请求生命周期和最终统计仍需遵守各自的现行结算规则。

## 3. 统一格式包含什么

| 层次 | 内容 | 推理用途 |
|---|---|---|
| 功能工作量 | 操作语义、宏指令/UOP 边界、寄存器依赖、访存地址与大小、实际分支方向 | 目标模型计算核心和内存时序 |
| 执行上下文 | 流类型、地址空间、权限域、有效的软件线程身份、预热和测量记录范围 | 解释功能流及初始化状态 |
| 稀疏因果事件 | 有可靠来源的创建、等待、释放、唤醒及其关联 | 在必要边界约束工作何时可以推进 |
| 能力与来源描述 | 生产者、ISA/ABI、转换规则版本、字段有效性、覆盖范围、采集边界 | 判断该输入适用于哪些模型和实验 |
| 审计信息 | 采集时间戳、原始调度、边界证明 | 离线诊断，或明确选择的固定调度实验 |

gem5 的 ROB 阻塞次数、cache 命中结果、实际访存延迟、预测错误和 CPI 属于验证数据，
不能作为微架构探索的时序答案输入。保留实际分支方向不等于保留原机器的预测结果。

用户态、用户态加内核两种输入可以使用同一格式，但必须声明各自覆盖范围。
不能因为格式支持内核记录，就为普通 DR 用户态 trace 填入虚构的内核工作。

## 4. 采集窗口与预测完成时间分离

现行 `first-core-target-common-end-v1` 继续决定采集的工作量：最快核达到 10M
测量用户 UOP 时，在共同事件关闭所有参与核心的采集和参考统计；各核实际记录数
可以不同。详见[项目语义规约](project-goal-and-semantic-contract.md)。

转换时保存这组实际记录范围。探索不同目标微架构时，完整处理同一组记录，
不根据新模型的快慢重新截取每核 10M，也不按原 gem5 tick 强制停止推理。

建议明确区分：

| 语义 | 含义 |
|---|---|
| `TRACE_END` | 该流的规定采集范围结束，后续工作未包含在输入中 |
| `THREAD_EXIT` | 采集明确观察到软件线程退出 |
| `BLOCK` | 软件线程进入等待状态，后续可能因事件或超时恢复 |

EOF 可对应 `TRACE_END`，不能自动生成 `THREAD_EXIT` 或 `BLOCK`。
所有规定流都耗尽后，可以结束“完成这组固定工作量”的实验。
在此定义下，某核先耗尽后不再生成新请求属于工作集边界条件；不能仅凭尾部
竞争减少认定代码错误，也不能将结果无条件解释为完整原始应用的运行时间。

共同起止事件、参考时间单位和 tick 仍应保留用于审计。不同来源的绝对时间戳
不能直接比较，也不能通过逐核平移指令来消除预测与采集的时间差。

## 5. 软件线程身份独立于文件分片

建议在数据集描述中明确流按物理核心还是软件线程组织，例如 `stream_kind`。
存储分片与语义身份分别表达：

- `stream_id`：定位文件及记录序号。
- 软件线程身份：包含进程/线程及生命周期信息，避免 TID 重用混淆。
- `address_space_id`：表达共享或隔离的地址空间。
- 核心身份：表达已知的绑定或观察到的映射，不代替软件线程身份。

按核心组织的 gem5 FST 可以保留；按线程组织的 DR trace 也可以使用同一套记录语义。
允许缺少软件线程身份的旧流继续用于既有固定核心映射模式，但不能声称它支持
线程级同步恢复、迁移或重新调度。

当前 TaoTrace 的 `getTraceThreadId()` 返回 `ThreadContext::contextId()`。
其部分旧 `THREAD_CREATE`、`SCHED_IN/OUT` 输出基于硬件上下文及首次出现，不能
直接当作 guest 软件线程生命周期。代码审计位置是隔离 gem5 工作树中
`src/cpu/o3/probe/tao_trace.cc` 的 `getTraceThreadId()`、
`maybeEmitThreadCreate()` 和 `maybeEmitSchedSwitch()`。

首次观察到某线程也不证明该线程刚被创建；采样开始时已存在的线程应表达为初始状态。

## 6. 稀疏事件保存因果关系，不复制原始时序

事件扩展优先表达可证明的关系，例如：

```text
线程 A：计算片段 A1 → 事件 e1：使线程 B 可运行 → 计算片段 A2
线程 B：等待 e1 → 计算片段 B1
```

`e1` 在目标微架构上的生效时间由模型计算。B 成为可运行后，还要满足核心可用等
目标执行条件；“已唤醒”与“已开始执行”必须分开。

事件语义建议包括 syscall 进入/返回、线程创建/退出、可能阻塞提示、确定阻塞、
恢复为可运行，以及存在可靠配对时的同步释放/获取关联。不是要求首版全部实现。

建议的逻辑字段包括：

- 事件 ID、类型、主体线程、可选目标线程。
- 主流定位：`stream_id`、记录序号，以及在记录之前还是之后生效。
- 可选同步对象身份、调用/等待实例 ID、前置事件 ID。
- 可选超时语义：应用请求的期限及时间域，不能用采集到的等待耗时代替。
- 字段有效性、信息来源和覆盖程度。

普通 `SCHED_IN/OUT` 可保留作调度观察；DSE 默认不把原始切换时间或完整切换次序
固定为必须复现的结果。需要固定调度重放时，应独立声明实验模式。

如果固定采集中的获锁次序才能保证片段仍然有效，应声明“固定同步结果下的时序探索”。
固定 trace 不能同时保证任意改变竞争获胜者后的数据值、分支路径和工作分配仍然正确。

跨越采样边界的等待需要记录其初始状态：前置条件已满足、由输入内事件触发，或
依赖窗口外未知事件。缺失关联不能通过假定已满足、永久等待或补原始时间差来掩盖。
依赖不闭合的输入不得声称支持完整的因果重放。

用户态自旋和已记录的内核处理指令仍是功能工作。若以后将某段工作替换为语义事件，
必须声明替代范围，避免既执行原指令又重复收取同一等待或处理开销。

## 7. gem5 和 DynamoRIO 的适配职责

| 信息 | gem5 FS | DynamoRIO |
|---|---|---|
| 指令与依赖 | 将实际提交指令转换为共同功能语义 | 离线解码并构造相同语义的 UOP 与依赖 |
| syscall | 已有编号、选择性参数和返回关联 | 映射实际存在的 syscall 与参数标记 |
| 软件线程身份 | 需要 guest 任务身份观察 | 使用 trace 的进程/线程身份并处理生命周期 |
| 确定阻塞与唤醒 | 需要观察 guest 内核任务状态和唤醒路径 | 仅在实际具有相应标记或已验证采集扩展时提供 |
| 等待对象与配对 | 按需观察 futex 等机制 | 参数可提供对象线索，但不自动证明完整配对 |
| 核心映射与时间戳 | 保存实际模拟观察值 | 保存采集观察值及其精度、来源 |

gem5 FS 的软件调度发生在 guest Linux 中，不能只靠 gem5 CPU 的
`suspendContext()`/`activateContext()` 恢复全部软件线程等待。
可研究在采集器侧添加只读语义探针，以 guest 内核版本、符号和任务结构布局适配，
并在可靠的架构状态观察点生成事件。

本地 gem5 的 ARM Linux 实现已有通过 `addKernelFuncEvent()` 在 `__switch_to`
处获取任务信息的先例，但当前 x86 TaoTrace 尚未因此自动具备完整调度事件。
Linux 的 `sched_waking`、`sched_wakeup` 和 `sched_switch` 分别表达不同阶段，
可作为适配器的语义依据；其中 `sched_wakeup` 不保证在原唤醒上下文中调用，
不能直接把当前线程填为完整因果来源。见
[Linux 调度事件定义](https://github.com/torvalds/linux/blob/master/include/trace/events/sched.h)。

DR 的格式能够表达 `SYSCALL_UNSCHEDULE`、`SYSCALL_SCHEDULE`、
`DIRECT_THREAD_SWITCH` 和 `SYSCALL_ARG_TIMEOUT`，但格式存在不等于任意采集文件
都具有这些标记。`MAYBE_BLOCKING_SYSCALL` 只表示可能阻塞。
`CORE_WAIT` 是调度器重放对齐产生的等待，不能转换为程序同步阻塞。见
[DR 标记定义](https://github.com/DynamoRIO/dynamorio/blob/master/clients/drcachesim/common/trace_entry.h)
及[调度器说明](https://dynamorio.org/sec_drcachesim_sched.html)。

例如普通 `FUTEX_WAKE(X, 1)` 的参数与成功返回只表明唤醒数量，不能单独指出
多个等待者中哪一个被唤醒；精确配对需要额外证据。见
[Linux FUTEX_WAKE 文档](https://man7.org/linux/man-pages/man2/futex_wake.2const.html)。

## 8. 能力声明与微架构探索范围

两种来源可以填写同一格式的不同信息子集。必须区分：

1. 字段已采集且值为零/否。
2. 字段未提供或未知。
3. 某类事件完整采集但没有发生。
4. 某类事件仅部分采集。

不能从“文件里没有唤醒事件”推导“整个执行没有唤醒”。消费者所需能力不满足时，
应拒绝该语义模式，或明确使用能力更有限的固定工作量模式。

物理地址、初始页表状态和内核覆盖也遵循相同规则。只有虚拟地址的 DR 输入不能
声称具备与物理地址完整输入相同的 cache/coherence/CHA 验证能力。

当前 FST 已经做了 UOP 转换，隐含固定的拆分规则。两种适配器需要记录并遵循
共同的转换规则版本；操作分类不应依赖未声明的生产者枚举变化。
在此基础上可研究已支持的核心和内存参数。若探索译码、UOP 拆分或融合机制，
需要保留足够的宏指令编码并重新转换，不能假定既有 UOP 流覆盖这些变化。

固定地址、分支和计算片段的可复用范围也必须声明。本文不声称能够从既有 trace
恢复改变数据竞争、软件调度或工作分配后产生的任意新执行路径。

## 9. 存储扩展与两阶段接入

保留 64 字节指令主记录、完整依赖附件和既有 syscall 元数据。
v7 的 syscall 表、偏移与文件大小都有严格检查，不将其尾部擅自解释为任意扩展区。

建议另设版本化事件附件，由数据集描述声明关联文件、版本、主流身份及其必要性。
关键语义附件缺失、关联错误或消费者不支持时，应拒绝需要该语义的执行。
旧 v7 文件在原有能力范围内继续有效，不能通过修改版本标签获得从未采集的信息。

事件按主流位置排序并顺序读取。空间成本主要取决于事件数量，不要求为每条 UOP
增加字段；事件行大小尚未确定，因此本文不承诺具体空间和吞吐收益。

第一阶段可预读事件并建立批次边界，但不能因预读到唤醒事件就提前放行其他流。
只有第二阶段确认事件对应工作已经接受并取得有效模拟时刻后，才能更新相关约束。
普通批次仍使用当前两阶段核心与内存推理，无须每条指令做全局同步。

事件扩展的格式支持和执行器支持需要分别声明。能读入事件不等于事件已经影响时序。

## 10. 起点过滤与现有数据处理

已确认当前采集代码存在测量开始后、CPL 初始化前过滤内核记录的路径；现行
[native kernel 规约](fst-native-kernel-trace.md)也记载了此处理。

这需要单独核查声明范围与实际工作是否一致，但不能与“各核首次退休时间不同”
混为一谈。后者本身正常；前者需要核查被过滤的指令是活动内核工作、idle，还是
原有 scope 有意排除的内容，并量化实际遗漏。

本文不改变该过滤逻辑，也不重新定义当前 CPI 分子。若后续确认应纳入的工作被丢弃，
需要成对修复采集、参考统计、转换和验证，不能只移动统计起点或补一段固定时间。

当前已采数据可继续用于现有能力和统计口径下的回归。先核查缺失及其影响，再决定
需要重采哪些样本；不因预测完成时间不同而删除或全量重采。

## 11. 后续实施优先级与最小验证

本节是后续工作的建议顺序，本次不执行。

1. **先落实语义规约。** 明确固定工作量、采集/推理边界、流与线程身份、EOF、
   字段有效性和能力声明；保留现行最快核 10M 共同采集结束策略。
2. **按需求定义最小事件扩展。** 选择有可靠来源且当前场景确实需要的事件，
   确定锚点、覆盖声明、跨边界关联和兼容策略，不一次实现完整调度系统。
3. **分别接生产者和消费者。** gem5 探针、DR 转换器、FST 读取器及两阶段执行器
   都必须通过各自的事件守恒与因果检查，避免“写进文件但没有生效”。
4. **独立处理采集起点。** 依据实际缺失证据确定是否修正 scope 内核工作覆盖。

实现后的必要验证建议：

- 用同一功能语义夹具验证两种适配器的指令、宏指令、依赖和事件含义一致，
  不要求不同真实采集运行产生逐字节相同文件。
- 用两线程用例改变前置计算延迟，验证依赖者随模型时间变化，且预读不会提前唤醒。
- 验证某流提前 EOF 不触发全局停止、不伪造退出或等待；必要事件附件缺失时明确失败。
- 仅对实际改动的执行路径做必要回归和代表性吞吐比较，不先重跑完整矩阵。

若形成新的精度报告，继续遵守[精度汇报规约](accuracy-reporting-contract.md)：
列出 CPI 相对误差及绝对误差 `abs(FastSim CPI - gem5 CPI)`，聚合同时报告 CPI MAE，
并保持 scope、实际宏指令分母和预热边界一致。本文没有新增实验结果。
