# SQLite C4：完整退休周期排查与误差来源（2026-10-20）

后续：[开启分支恢复后的完整残差账、恢复尾部局部缺口及 Zstd 同源开关结果](branch-recovery-sqlite-zstd-results-20261020.md)。本页原周期账对应关闭配置，不能当作开启后的残差构成。

本轮沿用[既有排查方法](buffer-tso-cpi-diagnosis-next-steps-20260924.md#8-下一步工作与验收顺序)：冻结来源与配置，构建完整 ROI 的互斥退休周期账，再用同次动态指令配对、源码和受控配置验证关键边。生产模型、默认开关及延迟常数未修改。

## 1. 已确认的结论

**发现一条能造成显著 CPI 低估的实际顺序错误：默认 response 路径允许已判误预测分支的正确路径 load，在分支解析前发射甚至完成。** SQLite 的 B-tree 字节解析与虚拟机执行反复触发这种路径。开启已有 response branch recovery，在同一原 FST 上净补回约 230 万 active cycles，误差缩小，但仍未消除。
完整窗口差额分布均匀，不支持以 ROI 开头冷启动作为主要解释。普通 store 生命周期及来源明确的完成到退休下界，对本案完整 CPI 的独立净影响很小。尚未完成剩余误差的独立因果分摊，不能把阶段差额全部改名为 branch、cache 或 DTLB 贡献。

## 2. 冻结来源、口径与采集资格

- 原始对照为刚重采的 SQLite：4 个单线程标准 rate 副本、4 核、8 通道、3 GiB、buffer TSO 114，官方参数及 ROI 不变，KVM → 100 万指令 warmup → stat。
- 阶段取证复用同一个新 checkpoint、同一 gem5 和 frozen runner。观察包装器在 stats reset 后打开已有 O3PipeView / DynInst 日志，不向目标添加时序事件。原生时间只用于离线诊断，不输入 FastSim。
- 阶段采集正常退出 0、解析器退出 0，无守卫中止；宿主耗时 1123.392 秒，其中 warmup 54.871 秒，新增正式 FST 3,021,522,400 bytes。海量原始 debug 文本流经 FIFO 后丢弃，只保留紧凑记录。

## 3. 全窗口互斥周期账

同一周期退休多条 UOP 只计一次；相邻退休边界间的时间互斥切分。不能累加每条指令重叠的等待来充当 CPI。“有退休的周期”只是退休发生的周期数，不是“有用工作”的独立因果贡献；更多周期各退休少量指令，也会让这一项增大。

| 时间落点 | gem5 cycles | FastSim cycles | gem5 − FastSim |
|---|---:|---:|---:|
| 有退休的周期 | 9,702,339 | 6,155,373 | +3,546,966 |
| 下一退休指令尚未取指 | 138,530 | 12,006 | +126,524 |
| 已取指、尚未最终发射 | 319,652 | 22,384 | +297,268 |
| load 已发射、尚未退休 | 13,388,683 | 12,025,852 | +1,362,831 |
| store 已发射、尚未退休 | 4,594 | 911 | +3,683 |
| 其他已发射、尚未退休 | 73,120 | 1,410 | +71,710 |
| 未知阶段 | 4 | 0 | +4 |
| 配对退休跨度合计 | 23,626,922 | 18,217,936 | +5,408,986 |

起点、终点 padding、线程归属等修正为 **-20,861.120120 cycles**，与配对跨度差相加严格得到 active 差 **5,388,124.879880 cycles**。未知阶段 **4 cycles** 保留，不摊入已知项。四核首尾没有漏配记录。

“有退休的周期”差约 355 万，load 发射后的等待差约 136 万。前者提示模型把退休压得更密，不能简单等同于 commit width 参数错误；提前完成的后继指令也会在队头解除后扎堆退休。

## 6. 具体反例：正确路径被过早执行

同一次短窗口中，`0x404800` 读取 B-tree 字节，随后测试符号位，`0x404810` 的 `jns` 决定是否转到 `0x404910`。模型在 ordinal 1775284 明确标记该分支 `branch_miss=1`，却让 ordinal 1775285 的正确目标 load 提前执行。下面各列都采用各自窗口原点，重点看同列的先后关系，不直接比较两列的绝对时刻。

| 事件 | native 周期 | 默认 FastSim 周期 |
|---|---:|---:|
| 分支发射 | 1488 | 418 |
| 目标 load 取指 | 1494 | 191 |
| 目标 load 发射 | 1498 | 252 |
| 目标 load 的模型完成 | 不把 native completeTick 当数据返回 | 255 |
| 分支模型解析完成 | — | 419 |

默认模型中，目标 load 比分支发射早 **166 cycles**，并在分支模型解析前完成。真实硬件可以在预测路径上投机，但对于模型自己判错的预测，不能提前使用 trace 已知的正确后继路径。这会让实际需等待的后续访问过度重叠，即使 cache miss 总数接近，也会低估总时间。
同一短 FST 开启 response branch recovery 后，这个例子的目标 load 只在分支模型完成后才发射，顺序反例消失。该原生日志没有独立逐分支预测结果位，因此 native 侧只声明观察到的阶段先后；模型侧已知误预测的顺序错误不依赖推测 native 预测结果。

## 7. 同一原始 FST 上的受控配置验证

| 配置 | gem5 CPI | FastSim CPI | 相对误差 | CPI 绝对误差 / 单案 MAE | 新增 active cycles | 原 active 缺口的净变化比例 |
|---|---:|---:|---:|---:|---:|---:|
| 默认 | 1.000925 | 0.773267 | -22.74% | 0.227658 | +0 | 0.00% |
| 仅 response branch recovery | 1.000925 | 0.870686 | -13.01% | 0.130239 | +2,298,153 | 42.79% |
| 仅普通 store lifecycle | 1.000925 | 0.773343 | -22.74% | 0.227582 | +1,788 | 0.03% |
| 仅来源映射的完成到退休下界 | 1.000925 | 0.777387 | -22.33% | 0.223538 | +97,208 | 1.81% |

每行是同一负载的一项独立配置对照，不是多个负载的 MAPE。分支恢复补回 2,298,153 active cycles，是当前已测试项中最大的净影响；默认未变。这些比例不是互斥因果份额，不能相加。开启分支恢复后仍低估约 13.01%，尚未恢复历史 7% 以内的结论。

完成到退休下界的 2 cycles 有明确来源：同次 config.ini 的 `iewToCommitDelay=1`，加上 `Commit::tick()` 先 `commit()` 后 `markCompletedInsts()`、新就绪位下一拍才消费的顺序。5088 个普通整数微操作的 issue→complete 最小值两边均为 1，complete→retire 最小值 native=2、模型=0。但全窗口该对照只净增加 97,208 cycles，说明局部边界差不能按指令条数直接外推 CPI。现有全局参数还影响 store/特殊操作，所以这不是已经验证的逐类修复，更不能因数值更近而直接改默认。

## 8. load 服务与依赖的短窗口证据

短窗口 core0 的 8192 条连续记录，使用同次 native v7 准入/回调事实与动态序号连接。审计回放的 active、elapsed、PMU 与无审计对照一致。配对支持 PC、程序顺序和原生动态序号关联，尚无独立访存地址/操作数身份认证；不升级为完整访存生命周期认证。

| 合格样本 | 数量 | native issue→response 中位数 | FastSim issue→response 中位数 |
|---|---:|---:|---:|
| 两边均走 L1 的 load | 1214 | 2 | 2 |
| 两边均走 DRAM 的 load | 13 | 186 | 164 |

1950 条 L1-load 功能依赖边，callback→消费者 issue 中位数两边均为 1；13 条 DRAM-load 依赖边也均为 1。暂不支持统一增加 L1 服务或唤醒常数。DRAM 样本 native issue→response 为 143–1201 cycles，模型均为 164；最极端样本跨越测量起点，不能当作稳态平均。另有一个 native L1-hit / 模型 DRAM 的路径分歧，说明错误有双向抵消。
短段互斥分区中的准入→回调差为 -17 cycles，回调后到退休差为 +290，不能把 13 条 DRAM 的时延差相加充当全 ROI 贡献。仍保留 114 条无原生时间戳、140 条 fragment 身份不足等排除项，不用 proxy path_class 补真值。

## 9. 哪些解释目前不成立，哪些仍未解释

- **CDA/NO_ACCESS：** 本次 SQLite 窗口没有 NO_ACCESS，不能套用 Zstd 的 CDA 根因。
- **主要是窗口开头冷启动：** 八段差额近乎均匀，不支持。
- **统计分母或边界造成主要低估：** 双方宏指令人口匹配、active owner 完整且 unknown=0，边界等修正仅约 2.09 万周期，无法解释约 539 万差额。仍不将所有 OS 间接影响宣称为已排除。
- **普通 store 生命周期是主因：** 当前独立对照只增加 1788 cycles，不支持它解释大部分差额。
- **统一再加两拍退休时间即可修好：** 有局部阶段证据，但全窗口净影响仅约 1.81%，不支持作为主要补偿。
- **miss 数接近意味着 CPI 应接近：** 不成立。服务时长、解析后正确路径的推进、错误路径资源占用与退休聚集都会影响 CPI。
- **剩余 13.01% 都来自 DRAM/DTLB：** 尚无充分证据。原生错误路径资源、redirect 到 fetch 的完整链、实际 cache 准入重排、DRAM 服务分布和状态传播仍需独立核对。

## 10. 后续修复顺序

1. 优先修分支解析 → redirect 到达 → 正确路径 fetch → 访存准入的因果链。用本次真实反例做机制回归，不把正确路径提前发射的访问仅在最后延长 response。
2. 核对已有 response branch recovery 的覆盖和剩余缺口：它目前是受约束的单遍响应路径选项，不代表错误路径资源与 canonical cache 请求时间已经完整重排。不能只因单案更准就改变所有负载默认。
3. 退休两拍边界按普通写回、store、特殊指令分别验证，避免把全局开关当作精确逐类实现。优先级低于已确认的过早正确路径推进。
4. 对剩余差额增加逐分支原生预测/redirect 与实际请求准入证据，并扩大同次服务样本；继续使用完整窗口周期账检查正负误差与补偿，再回归其他负载并独立测吞吐。

## 11. 诊断工具与存储收尾

原生阶段日志包含窗口前已退休但后来才释放的指令，以及共同终点后的 drain 指令。直接按 PC 在 SQLite 的重复循环中找起点会歧义；本轮先按退休 tick 筛选测量边界，再要求逐条 PC/程序顺序一致。共同终点同 tick 的额外尾记录单列，不插值、不跳过内部错配。新增边界/重复循环回归先失败再通过，合计 16 项解析/配对/守恒测试通过。
原生 full capture 与解析器均正常退出；FastSim 原始源和同次新源的阶段导出均与生产预测完全中性。生产源码和二进制哈希未变。完成到退休对照首次 setup 错认配置中的 CPU type 为 X86O3CPU，实际为 BaseO3CPU，导致一次缺配置的验证失败；失败日志保留，最终有效对照使用独立目录通过，未放宽来源门禁。
FST 总量 **28,603,001,344 bytes（28.60 GB）**，磁盘剩余 **409.88 GB**。低于 100 GB 上限；保留有效原始输入。阶段插桩和审计耗时不是新吞吐测量。
